## 4. 🔴 缺陷 1：应用内容被状态栏 / 导航栏压住

真机截图里，应用自己的菜单栏（`文件 编辑 轨道 视图 选项 帮助 语言`）与系统状态栏（时钟 `19:47:22`、
`1.60 MB/s`、`5G`、电量）画在**同一行**；底部状态文字 `运行时信息已更新` 同理被导航栏压住。
模拟器截图里看不到这个现象，所以这是**真机才暴露**的问题。

### 硬数据（`dumpsys window`）

```
StatusBar   frame=[Rect(0, 0 - 1080, 120)]        ← 高 120 px = 40 dp = 40 CSS px
NavigationBar frame=[Rect(0, 2244 - 1080, 2376)]  ← 高 132 px = 44 dp = 44 CSS px
DisplayCutout insets=Rect(0, 120 - 0, 0)          ← 顶部中央刘海区（x 508–572）
MainActivity frame=[Rect(0, 0 - 1080, 2376)]      ← 🔴 应用窗口 = 整块屏幕，从 y=0 开始，没有任何 inset
```

### 根因

`targetSdk=36`。**从 API 35 起，targetSdk ≥ 35 的应用被强制 edge-to-edge**：系统不再为应用预留
状态栏/导航栏区域，而是把整块屏幕交给应用、把系统栏浮在上面。上游是桌面应用，从未处理过 inset
（桌面没有这一层），于是菜单栏直接落在状态区下面。

### 影响

- 顶部 40 CSS px、底部 44 CSS px 的内容**不可用**：菜单栏第一批项（`文件`/`编辑`）被时钟遮挡，
  点击还会与系统栏的手势区冲突。
- 这不是"排版挤"，是**窗口几何**问题 —— 三套布局（phone/tablet/desktop）都躲不过，必须先单独修。

### 修复选项

| 方案 | 落点 | 代价 / 风险 |
|---|---|---|
| **A（推荐）** Activity 里施加 inset padding | `gen/android` 生成物 → 由 `setup-gen-android.sh` **脚本重放**（同 `BuildTask.kt` 的既有做法） | 与三套布局正交，一处生效；只改生成物，不碰 `upstream-src` 源 |
| B `viewport-fit=cover` + `env(safe-area-inset-*)` | 前端（走 patch） | 需要实测 WebView 是否把真实 inset 暴露给 `env()` |
| C 主题里 `windowOptOutEdgeToEdgeEnforcement=true` | `styles.xml`（生成物） | 最省事，但 API 36 已废弃该开关，只能当过渡 |

## 5. 🔴 缺陷 2：`ResizeObserver` 反馈环 58.8 条/秒

干净窗口实测（强停 → 删日志 → `am start` → 21 秒 → 立刻快照）：

| 指标 | 真机 221deeb | 模拟器 hs-phone-tall |
|---|---|---|
| 窗口 | 21 s | 30 s |
| 总行数 | 1255 | 857 |
| ERROR 行 | **1235** | 832 |
| 归并后种类 | **1** | 1 |
| 速率 | **58.8 条/秒** | 27.7 条/秒 |
| 其余 | 全部 INFO/WARN | 同 |

```
[ERROR] backend_lib::commands::diagnostics: [frontend] Uncaught error:
        ResizeObserver loop completed with undelivered notifications. | detail: http://tauri.localhost/:0:0
```

### 判读

- **只有一类错误**，占日志 98.4%。既不是后端崩溃，也不是模型/音频问题。
- 速率与**帧率同量级**：真机是 120 Hz 屏（logcat 里 VRR `ActiveFPS: 90`）→ 58.8/s；
  模拟器 60 Hz 且软件光栅化 → 27.7/s。**"每帧一次"的特征**说明布局从未收敛，
  而不是偶发抖动。
- 触发点最可能是 `timelineKernelHost.ts:5239` 的 `ResizeObserver`：它的回调写回
  `viewportWidthPx` 并 `onViewportWidthChange?.()` 通知 React，而 React 重渲染又改变容器宽度
  → 下一帧再来一次。
- **根因仍是"桌面布局塞进 360 px"**：横向溢出导致滚动条/容器宽度在两个值之间来回切换，
  这正是 `ResizeObserver loop` 的典型成因。也就是说这条报错不是独立 bug，
  而是 `docs/04` 判定"必须做三套布局"的**量化证据**——修好布局它应自行消失。

### 附带影响

- 每帧一次布局抖动 ⇒ 电量与发热，且在 120 Hz 屏上更严重。
- 日志被刷爆：21 秒 1255 行里 1235 行是噪声，**后续任何真机排查都会被它淹没**
  （这也是 `run-app.sh` 现在会输出"错误摘要"的原因）。

### 内存

PSS 518 MB（30 s 观测）→ 615 MB（后续观测），Native Heap 261 → 306 MB。
**样本不足以判定泄漏**，但方向可疑（与报错环同时增长）。要下结论需要固定窗口的多次采样。

## 6. ⚠️ 待改进：首启 `pre-warm` 与资源拷贝抢跑

首次启动（模型还没拷到私有目录）时：

```
[INFO]  platform::resources: 拷贝 models/nsf_hifigan/pc_nsf_hifigan.onnx → …（53 MB）
[WARN]  nsf_hifigan_onnx: [nsf_hifigan] session pre-warm failed: NSF-HiFiGAN ONNX model not found. …
[WARN]  fcpe_onnx:        [fcpe] session pre-warm failed: FCPE ONNX model not found. …
[WARN]  hnsep_onnx:       [hnsep] session pre-warm failed: HNSEP ONNX model not found. …
[INFO]  platform::resources: 模型就绪：拷贝 5 / 跳过 0 / 缺失 0，耗时 939 ms
…（随后三个 session 仍正常 created session）
```

顺序问题：**三个 `pre-warm` 跑在资源拷贝完成之前**，于是首启的预热全部落空，session 改由
后面的正常路径建立，还多触发一次
`inference device changed during session build — rebuilding with the new EP`（白建一次）。

功能上不致命（后续 `created session` 都成功），但首启多花一次建 session 的时间、
且日志出现三条看起来像"模型找不到"的 WARN，容易误导排查。
修法：把 `resolve_asset_root()` 提到 `pre-warm` 之前（`lib.rs` 的 `setup()` 里两处调序即可）。

## 7. 下一步建议顺序

1. **修 inset（A 方案）** —— 窗口几何是布局的前提，先解决，否则三套布局做完还要返工。
2. **核实 ResizeObserver 触发点** —— 在布局改造前先取一次基线（本文件的数据就是基线）。
3. **调 `setup()` 里资源拷贝与 pre-warm 的顺序** —— 一行级改动，顺手做掉。
4. 之后才进 `docs/04` 的三套布局 + `docs/11` 的 SAF。

## 8. 🔧 缺陷 1 的修复与验证（已闭环）

### 8.1 根因比 §4 更直接

`gen/android/.../MainActivity.kt` 里，**Tauri 模板自己主动调了 `enableEdgeToEdge()`**：

```kotlin
class MainActivity : TauriActivity() {
  override fun onCreate(savedInstanceState: Bundle?) {
    enableEdgeToEdge()          // ← 模板自带
    super.onCreate(savedInstanceState)
  }
}
```

所以不只是"targetSdk 36 被强制"，是模板**显式**开了 edge-to-edge，而它只适合
"内容本就该铺满全屏"的 WebView 应用。上游是桌面 UI 搬过来的，于是必然被系统栏压住。

### 8.2 为什么 padding 能作用到 WebView

wry 挂载 WebView 用的是 `Activity.setContentView(webview)`
（`wry/src/android/main_pipe.rs` 的 `"setContentView"` JNI 调用），
因此 **WebView 就是 `android.R.id.content` 这个 FrameLayout 的子 View**。
给父容器加 padding，等于把整个前端视口收缩进安全区 —— **不必碰 WebView 本身**。

### 8.3 改动落点（可重放，不碰上游源码）

`scripts/setup-gen-android.sh` 新增 §7（幂等，带 `HS-SAFE-AREA-PATCH` 标记），
重写 `MainActivity.kt` 并补两个颜色资源：

| 内容 | 说明 |
| :--- | :--- |
| `systemBars + displayCutout + ime` 各边取 max → `setPadding` 到 `android.R.id.content` | 四边一次垫完 |
| **ime 也垫** | `enableEdgeToEdge()` 之后框架**不再自动 `adjustResize`**，不自己处理软键盘会盖住输入框 |
| 窗口背景 = `hs_chrome` 资源（`values/`=#F2F3F6、`values-night/`=#353535） | **API 35+ 会忽略 `SystemBarStyle` 的 scrim 颜色、强制透明系统栏**，空出来那条露出的是窗口背景；不设就是 DayNight 的白色，深色应用上一条白带 |
| 系统栏图标明暗随 night 切换 | `SystemBarStyle.dark/light`。上游 `AppThemeProvider` 默认跟随 `prefers-color-scheme`，映射对齐 |
| `onResume` 重新 `requestApplyInsets` | 旋转 / 分屏 / 手势导航切换 / 深浅色切换都会改变 inset |

### 8.4 验证（客观量测，非肉眼）

新增 `scripts/measure-inset.py`，两个判据：

**主判据 —— 整体垂直位移搜索**（行亮度签名，找 after 相对 before 的下移量）：

```
d= 120  MSE=  182.23   ← 最佳
d= 121  MSE=  190.30
d= 119  MSE=  190.43       期望 = 状态栏高度 120 px
⇒ ✅ 一致：界面被顶下了整整一个状态栏
```

**底部判据 —— 导航栏条带内的内容残留**（左带逐行标准差 > 6 视为有内容）：

| | 导航栏条带 `y∈[2244,2376)` 内"有内容"的行数 |
| :--- | :--- |
| 修复前 | **108 / 132**（最后一条 y=2357，应用内容越过导航栏顶边 2244） |
| 修复后 | **18 / 132**，且条带底部均亮度 = **53.0** = `#353535` = `hs_chrome` |

那 18 行是过渡带（sd≈6.5、均亮度 53.5 vs 背景 53.0），实质无内容 ——
即条带底下露出的已经是**窗口背景**而不是应用内容。

**软键盘**：点击 `BPM` 输入框 → 键盘弹出，应用视口正确收缩到键盘之上，
底部状态条紧贴键盘顶边（既没被盖住、也没有双重内缩的空隙）——
证明 `ime()` 的处理是对的。见 `docs/screenshots/真机-inset修复后-软键盘.png`。

### 8.5 ⚠️ 副作用：可用视口从 360×792 变成 **360×708** CSS px

```
1080×2376 px @density 3  →  360×792 CSS
减 statusBar 120 px + navBar 132 px = 252 px = 84 CSS px
可用视口 = 360 × 708 CSS px      （高度少 84 px，−10.6%）
```

**`docs/04` 的三套布局必须按 708 来设计，不能按 792。** 这也是把 inset 排在布局之前的
直接理由 —— 否则布局做完要按新的可用高度整体返工。

### 8.6 与 `ResizeObserver` 反馈环的关系：**无关**

| | ERROR 速率（干净窗口） |
| :--- | :--- |
| inset 修复前 | 58.8 条/秒 |
| inset 修复后 | **58.6 条/秒** |

视口高度少了 84 px，速率几乎没变 ⇒ 反馈环由**桌面布局的横向溢出**驱动，
不由 inset 驱动。**它仍然是 `docs/04` 三套布局的 KPI，不是本项能顺带修掉的。**

### 8.8 途中修掉的两个构建/脚本坑

1. **`javaCompile.lock` 被拒访问**，报的是
   `Could not create service of type GeneralCompileCaches` —— 极易误读成"缓存坏了"。
   真因是上一次**中断的构建**留下的陈旧 Gradle 锁，而本机沙箱对 `*.lock`/`*.lck`
   的打开方式敏感。修法：`build-apk.sh` 新增 §⑥.6，构建前清 `$GRADLE_USER_HOME/caches`
   下的 `*.lock`。**判定很干净：陈旧的能删、在用中的删不掉（Windows 直接拒绝）**，
   所以无条件尝试删除是安全的 —— 实测一次清掉 **10 个**。
   （注意与 wrapper 那个 `.lck` 不同：那个**连删都删不掉**。）
2. **写 Kotlin 的 heredoc 必须带引号**（`<<'KT'`）。不带引号时 KDoc 里的反引号会被
   shell 当命令替换执行 —— 实测真的把 `` `tauri android init` `` 当命令跑了一次
   （`tauri: command not found`），而且那段文字被替换成空。包名改用占位符 + `sed` 代入。
   顺带把脚本改成**从 `build.gradle.kts` 的 `namespace` 推导路径**，不再依赖
   `MainActivity.kt` 已存在。
