# 04 · 小屏排版适配方案

> 用户提出的三个具体问题：**① 显示不全的文字 ② 被遮挡的元素 ③ 难以点击的小按钮**。
> 本文先用量化数据把这三类问题定位到具体文件，再给改造方案。

---

## 1. 现状量化（问题定位）

| 指标 | 实测值 | 对应的问题类别 |
| :--- | :--- | :--- |
| CSS `@media` 查询 | **0 处** | 全前端无任何响应式设计，桌面 1400×900 布局直接压到手机上 |
| Tailwind 硬编码字号 | **98 处**：`text-[10px]`×45、`text-[12px]`×24、`text-[11px]`×20、`text-[9px]`×7、`text-[13px]`×2 | ① 文字过小。**9 px / 10 px 在手机上基本不可读** |
| `data-tooltip` | **91 处** | ① 长文本靠 tooltip 补全，而 tooltip 是 hover 触发 → 触屏上完全失效 |
| `truncate`（省略号截断） | **49 处** | ① 文字显示不全的**直接来源**：49 处截断 + 91 处 tooltip 失效 = 信息永久丢失 |
| `hover:` 状态 | 116 处 | ③ 触屏无 hover，大量视觉反馈失效 |
| 固定/最小宽度 | `max-w-[920px]`×3、`w-[420px]`、`w-[380px]`、`max-w-[760]`、`max-w-[620]`、`min-w-[140~220px]`×12 | ② 360 CSS px 宽的手机上必然横向溢出 |
| 固定网格列 | `grid-cols-[64px_minmax(0,1fr)_76px_64px_84px_48px]`（`App.tsx:3184/3234`） | ② 固定 6 列共 336 px + gap，手机上放不下 |
| `h-screen w-screen` | 3 处 | ② 未考虑安全区，内容会被状态栏/手势条遮挡 |
| `min-h-[200px]`（时间线）/ `min-h-[150px]` | 2 处 | ② 双面板各占 200/150 px 最小高，竖屏手机上直接挤爆 |
| 对话框组件 | **16+ 个**（`ExportAudioDialog` / `ImportProjectDialog` / `BenchmarkDialog` / `KeybindingsDialog` / `TimelineDisplaySettingsDialog` / `SnapGridSettingsDialog` / `RecordingSettingsDialog` / `SplitTransitionSettingsDialog` / `CustomScaleDialog` / `AutoBackupDialog` / `PitchSnapSettingsDialog` / `MidiTrackSelectDialog` / `QuickClipExportDialog` / `AppearanceSettingsDialog` / `EditDialogs` + 各类 ContextMenu） | ③ 全部是桌面尺寸的模态框 |
| `MenuBar.tsx` 下拉菜单 | `w-[380px] max-w-[92vw]`、`w-[420px] max-w-[92vw]` | ② 已有 `max-w-[92vw]` 兜底（上游有一点移动意识），但**菜单是桌面菜单栏语义，手机上没有顶部菜单栏习惯** |
| 默认窗口 | 1400 × 900 | 参考：手机竖屏 ≈ 360 × 800 CSS px（1080×2400 物理 / DPR 3） |

### 结论：三类问题都真实存在，且都不是"个别组件没调好"，而是**架构级缺失响应式层**

## 2. 断点设计

```ts
// frontend/src/touch/layoutMode.ts
export type LayoutMode = "phone" | "tablet" | "desktop";

export function resolveLayoutMode(w: number, h: number, forced?: string): LayoutMode {
    if (forced) return forced as LayoutMode;   // ?layout=phone|tablet|desktop，便于调试
    if (w >= 1280) return "desktop";           // 上游现有布局，一行不改
    if (w >= 600 && h >= 500) return "tablet"; // 可停靠多面板
    return "phone";                            // 单面板 + 底部页签
}
```

判据不只看宽度，还要看**可用高度**（横屏手机高度可能只有 360 px，塞不下双面板）：

| 形态 | 宽度 / 高度 | 布局 | 同屏面板数 |
| :--- | :--- | :--- | :--- |
| 手机竖屏 | w < 600 | **单面板 + 底部页签 + 常驻播放条**；时间线与参数面板**互斥显示** | 1 |
| 手机横屏 | w < 600（或 w 600–900 但 h < 500） | 同上（横向空间够、纵向不够，仍不并排） | 1 |
| **平板** | w ≥ 600 且 h ≥ 500 | **可停靠多面板 + 可拖动分隔条 + 可折叠侧栏**；时间线与参数面板**同时可见** | 2–3 |
| 桌面 | w ≥ 1280 | 上游现有布局 | 上游原样 |

**关键决策：手机竖屏下时间线与参数面板必须互斥（页签切换），不能并排。**
理由：时间线需要的最小有效高度是 ~250 px（轨道 64 px × 3 + 标尺 + 工具栏），参数面板需要 ~300 px（钢琴键 + 参数轨）。竖屏 800 px 减去播放条(56) + 工具条(48) + 页签(56) + 安全区(~80) = 560 px 可用，两块塞不下。

**关键决策 2（依 Q1）：平板不是手机布局的放大。**
平板的价值是「同屏面板数 1 → 2~3」与「信息密度提升」，**不是把控件和字号放大或缩小**。
- 触摸目标仍 ≥ 44 px、正文仍 ≥ 16 px（平板也是手指操作）
- 差异体现在：轨道头显示更多元数据、参数面板钢琴键更宽并带音名、侧栏常驻、工具栏展开为图标行、时间线默认缩放更"缩小"（利用面积显示更多时间）
- **反向要求（写进 code review 检查项）**：不允许为了让平板塞下更多内容而把控件/字号压到桌面尺寸

参照依据与 FLM 事实核对表见 [07 文档 §2](07-决策落地与FLM式自适应布局.md)。

## 4. 字号与间距重标定

98 处硬编码 px 字号保留一种做法即可：**引入一串语义化 CSS 变量，桌面值与移动值不同，然后把硬编码 px 逐步替换为变量**。

```css
/* index.css */
:root {
    --fs-micro: 10px;   /* 辅助徽标、单位 */
    --fs-tiny:  11px;   /* 时间线刻度、次要信息 */
    --fs-small: 12px;   /* 次级文本 */
    --fs-base:  14px;   /* 正文（现状 text-sm） */
    --fs-lg:    16px;   /* 标题 */
    --touch-target: 24px;
}
[data-mobile="true"] {
    --fs-micro: 12px;   /* 手机下限：12 CSS px ≈ 4.2 mm，勉强可读 */
    --fs-tiny:  13px;
    --fs-small: 14px;
    --fs-base:  16px;   /* 16px 是 Android 推荐的正文下限 */
    --fs-lg:    18px;
    --touch-target: 48px;
}
```

| 现状类名 | 桌面 | 移动 | 说明 |
| :--- | ---: | ---: | :--- |
| `text-[9px]`（7 处） | 9 | **12** | 9 px 在手机上不可读，必须提升 |
| `text-[10px]`（45 处） | 10 | **12** | 同上，这是最集中的一处 |
| `text-[11px]`（20 处） | 11 | **13** | |
| `text-[12px]`（24 处） | 12 | **14** | |
| `text-[13px]`（2 处） | 13 | **15** | |
| `text-sm`（Tailwind 默认 14） | 14 | **16** | |

> 注意：**放大字号必然加剧溢出**。所以字号调整必须与 §6 的溢出治理**同时进行**，否则会把"字太小"换成"字被截断"。

## 5. 触摸目标规范

Android Material 规范：**最小 48 × 48 dp**（iOS 是 44 pt）。当前 Tailwind 里 `h-6` = 24 px、`px-1 py-0.5` ≈ 20 px 高的按钮**大量存在**（`App.tsx:3050/3142/3237/3322` 等处）。

| 元素 | 现状 | 移动目标 |
| :--- | :--- | :--- |
| 音频块左上角 `M` 静音按钮 | 很小（约 12–16 px） | ≥ 44 px，或移入浮动工具条 |
| 音频块角部淡入淡出把手 | 小三角形 | **渲染尺寸可小，但 hitbox ≥ 44 px**（用透明 padding 扩大） |
| 增益旋钮 | 小圆点，竖拖 | 移入浮动工具条做数值步进 |
| 小眼睛（面板可见性） | 小图标 | ≥ 44 px |
| 轨道 `C` 按钮 | 小方块 | ≥ 44 px |
| 参数面板的 `IconButton`（`size="1"`，Radix 最小档） | 约 24 px | 提升到 `size="2"`/`"3"`，或加透明 hitbox |
| 工具栏图标按钮 | `h-6`（24 px） | ≥ 44 px |
| 表格行内的状态徽标 | `text-[10px] px-1 py-0.5` | 只读徽标可保留小尺寸（非点击目标） |

**做法建议**：不逐个改 `h-6`，而是定义一个 Tailwind 组件类：

```css
.touch-btn {
    min-width: var(--touch-target);
    min-height: var(--touch-target);
    display: inline-flex; align-items: center; justify-content: center;
}
```
套在移动端分支的所有按钮上，视觉尺寸可以仍小，但 hitbox 达标。

## 6. 「显示不全的文字」专项治理（49 处 `truncate` + 91 处 `data-tooltip`）

这是用户最关心的问题之一，需要专门方案。

### 6.1 问题机理

现状模式是：`<div className="truncate" data-tooltip={longPath}>短文本…</div>`
- 桌面：文字被截断，鼠标悬停 → tooltip 显示全量信息。**可用**。
- 触屏：文字被截断，**没有悬停** → **全量信息永久不可达**。这是真正的"显示不全"。

`AppTooltip.tsx` 监听的是 `pointerover` / `pointermove` / `pointerout`。在触屏上这三个事件在**手指按下时触发、抬起时消失**，所以 tooltip 会一闪而过——比"不显示"更糟。

### 6.2 三种解法（按优先级）

| 方案 | 做法 | 适用 |
| :--- | :--- | :--- |
| **① 允许换行（首选）** | 移动端把 `truncate` 换成 `line-clamp-2` 或 `break-all`，靠增加行数容纳完整信息 | 文件名、轨道名、参数名 |
| **② 点击展开** | 改 `AppTooltip` 在触摸设备上为「点按显示 / 再次点按或点空白关闭」，并延长停留时间 | 需要完整展示又无法换行的场合（长路径、长参数说明） |
| **③ 移入详情面板** | 触屏上把长信息放到一个可展开的详情抽屉/底部面板 | 结构复杂的信息（工程列表 `App.tsx:3184` 那种表格） |

**改造点**：`AppTooltip.tsx` 增加 `IS_TOUCH` 分支，把 `pointerover` 触发改为 `pointerdown`（tap）触发 + 外部点击关闭 + 3 秒自动消失 + 可手动关闭按钮。这一处改动能一次性修复 91 个 tooltip 的可用性。

### 6.3 逐处检查清单（形成对照表）

建议按这个顺序逐个过：
1. 时间线：音频块文件名、轨道名、`ClipItem` 上的 dB / 时长文本
2. 参数面板：参数名、当前值、单位
3. `FileBrowserPanel`：文件名（最长的一批）
4. 工程列表（`App.tsx:3184` 那个 6 列网格）
5. 所有对话框的字段标签
6. 设置页的长说明文本

每处理一处，在对照表里记：原文本 → 移动端方案（换行/点击展开/详情面板）→ 是否验证。

## 7. 「被遮挡」专项治理

| 遮挡来源 | 具体问题 | 方案 |
| :--- | :--- | :--- |
| **状态栏 / 挖孔** | `h-screen` 未加安全区，顶部工具栏会被状态栏盖住 | `padding-top: env(safe-area-inset-top)`；`viewport-fit=cover` |
| **手势条 / 虚拟导航栏** | 底部页签会被系统手势条压住 | `padding-bottom: env(safe-area-inset-bottom)` |
| **软键盘** | 输入框在屏幕下半部时被键盘顶住；`100vh` 在键盘弹出时不收缩 | 用 `visualViewport.height` 动态设高度，或 Android `adjustResize`；输入框自动 `scrollIntoView` |
| **双面板互相挤压** | `TimelinePanel` 的 `min-h-[200px]` + 参数面板的 `min-h-[150px]`，在 560 px 可用高度下必然溢出/重叠 | 竖屏改互斥页签（§2） |
| **固定宽度对话框超屏** | `max-w-[760]`/`max-w-[620]`/`w-[420px]`/`w-[380px]`/`max-w-[920px]` | 移动端全部改为**全屏 Sheet**（底部上滑或全屏模态），而非居中弹窗 |
| **6 列固定网格** | `App.tsx:3184/3234` 的 `grid-cols-[64px_minmax(0,1fr)_76px_64px_84px_48px]` 合计 336 px + gap > 360 px 屏宽 | 改为**卡片式纵向列表**（每条一块卡片，字段上下排列），移动端不追平行表 |
| **下拉菜单超出屏幕** | `w-[420px] max-w-[92vw]` | 已有兜底，但应改为**底部 ActionSheet**（从下往上滑）更符合手机习惯 |
| **ContextMenu 定位** | 菜单按鼠标坐标定位，靠近屏幕边缘时溢出 | 移动端统一改为**底部 Sheet**，彻底回避定位问题 |
| **多窗口（AppearanceWindow）** | 桌面用独立窗口，Android 上会变成奇怪的浮动层 | 改为应用内全屏页（已在 02 文档列为移除项） |

## 8. 「难以点击的小按钮」专项治理

见 §5 的尺寸表。补充三条工程实践：

1. **hitbox 与视觉解耦**：用伪元素或透明 padding 扩大 hitbox，不必把图标本身做大（避免破坏视觉密度）。
   ```css
   .hitbox-44::after {
       content: ""; position: absolute; inset: -12px; /* 视觉不变，命中区变大 */
   }
   ```
2. **间距即防误触**：相邻可点目标的中心距 ≥ 48 px。时间线上密集的小控件（淡入淡出把手、`M`、增益旋钮）最容易误触——建议在手机上**把它们收进浮动工具条**，块体上只保留拖动。
3. **触屏上的"精确操作"要用辅助 UI 代替手势**：增益（dB）、参数值这类需要精细控制的东西，应当提供**步进按钮 / 滑杆放大镜 / 数值输入**，而不是让用户在 4 mm 的范围内竖拖。

## 11. 与触控方案的关系

## 13. 第二轮：∨ 菜单 / 👁 菜单 / 菜单补齐的实测修复（2026-09-21 第二批）

用户第 18 条口径落地后逐项上机验收，**抓到三个"功能写了但用户根本够不着"的缺陷**。
三个都属于同一类问题：**控件存在、逻辑正确，但几何位置在屏幕外或有内容溢出** ——
只有把 rect 量出来才会暴露（截图里"看着像没做"）。

### 13.1 🔴 `∨` 菜单：整组溢出 333px，「气声」之后的参数全在屏幕外

`∨` 菜单的实现是**整块复用**桌面参数工具栏（`.hs-param-rows` + `.hs-param-toolbar`），
靠 `body[data-hs-param-menu="open"]` 把它重排成底栏上方的浮层。原实现只给外层加了
`flex-wrap: wrap`，但**直接子元素是「分组容器」**（head 里一个 464px 宽、toolbar 里一个 678px 宽），
它们自己 `flex-shrink: 0` + 单行 nowrap ⇒ 整组撑破 330px 的浮层：

| 分组 | 实测宽度 | 溢出 |
| :--- | ---: | ---: |
| `.hs-param-head` 内的组（含「平滑度」） | 464 px | 127 px（百分比读数看不到） |
| `.hs-param-toolbar` 内的组 | 678 px | **333 px**（「气声」之后的张力/音量/声像全在屏幕外） |

**修法两条**（`index.css` 手机媒体查询内）：

1. 内层分组也要能收缩 + 换行：`flex-wrap: wrap; flex-shrink: 1; min-width: 0; max-width: 100%`
   （只给外层 wrap 是不够的 —— 这是本轮踩的坑）；
2. **参数选择胶囊（`.param-pill`）不进 ∨ 菜单**：用户口径里 ∨ 的内容是
   「同步位置 / 拖动方向 / 平滑度 / 参考轨道组 / 导入 MIDI / 算法」，参考图里没有参数选择；
   而「切换到某参数」已由 👁 竖排面板承担 —— 这里再来一份既重复、又正是 333px 溢出的元凶。

修后浮层内**零溢出**，全部元素落在 360px 视口内（`_inject-css.mjs --measure` 逐元素核对）。

### 13.2 🔴 👁 菜单：整块面板渲染在 y = −314 … 45（几乎全在屏幕外）

`VerticalDualPanel` 原来是 `position: absolute; bottom: 100%`，挂在参数工具行里 ——
那是**向上**展开。9 行 359px 高的面板放在 45px 高的工具行上方，实测 rect 是
`y = −314 … 45`：**只剩最后一行可见**，用户点不到任何「切换到/显隐」。

修法：改成固定浮层，从参数工具行下方开始（`top: 88` = 顶栏 44 + 工具行 40 + 4），
左右各留 4px，`max-height: calc(100vh - 196px)` 并内部滚动。修后 rect 为 `y = 88 … 447` ✓

### 13.3 🔴 👁 菜单的参数表是硬编码的，与算法不匹配（「切换到气声」静默失效）

初版把参数写死为 `pitch / formant_shift_cents / breathiness / tension / volume / pan`，
但**参数 id 随算法变化**：nsf-hifigan 下气声是 `breath_gain`、张力是 `hifigan_tension`，
根本没有 `breathiness`（那是 vslib 的）。于是「切换到气声」会去切一个不存在的参数。

修法：**改为镜像驱动**。`PianoRollPanel` 把真实状态写到 `window.__hsParamUiState`
（并在每次变化时派发 `hs-param-ui-state`），外壳只负责渲染与派发意图事件：

| 方向 | 通道 | 内容 |
| :--- | :--- | :--- |
| 面板 → 外壳 | `window.__hsParamUiState` + `hs-param-ui-state` 事件 | `editParam` / `params[{id,label,secondary,hasBreathSwitch,breathOn}]` |
| 外壳 → 面板 | `hs-set-secondary-param` `{param, visible}` | 单个参数的曲线显隐 |
| 外壳 → 面板 | `hs-set-static-param` `{id, value}` | 静态参数（气声 `breath_enabled` 0/1） |

这样「显隐」与「气声开关」都是**真状态**（不再是不生效的组件本地态），
且参数集合天然随算法变化。实测：点击「切换到」→ `editParam` 从 `pitch` 变为
`formant_shift_cents` ✓；点显隐 → 该参数 `secondary` 翻转 ✓；点气声「关闭」→ `breathOn: true` ✓。

### 14.5 🔴 非音高参数左侧「钢琴」换数值轴：上游本来就有，是**没接线**

用户口径：「切换到非音高时左侧的钢琴应该换为数值」。

排查发现上游的数值轴**已经完整存在**：
`pianoRollKernelHost.rebuildAxisMarkGeometry`（刻度线）+ `collectAxisTextRequests`
（标签）+ `buildAxisMarkInstances`，且 `resolveAxisKind(任意参数)` 会回退到
`"fallback"`（nice step）。**但** `PianoRollPanel.buildGridSpec` 的 kind 只认
`pitch / cents / degrees / formantCents` 四类，**顶层声码器参数**（共振峰 `formant_shift_cents`、
气声 `breath_gain`、张力 `hifigan_tension`、音量、声像）直接 `return null` ——
于是内核拿不到 grid spec：数值轴不画，**键盘还会残留在画布上**（正是
`pianoRollKernelHost` 注释里警告的那种情况）。

修法（三处，都是"接线"而不是重写）：
1. `PianoRollGridSpec.kind` 联合加 `"value"`；
2. `gridInstances.ValueGridKind` 加 `"value"`，并给网格步进一个**自适应**分支
   `resolveGridSpec()` —— 通用参数跨度跨数量级（volume 0..2 vs formant ±1200），
   固定步长不是太密就是太疏，且那个 `for` 循环**没有条数上限**，
   ⇒ 用 `niceAxisStep(span, 4)`（与数值轴标签同一套）并以 `span / 500` 兜底；
3. `buildGridSpec` 的 `kind` 末档由 `null` 改成 `"value"`。

实测：切到「共振峰偏移」后，左侧列显示 `400 / 200 / 0 / -200 / -400`

### 15.3 外观设置：移动端**已落地**（2026-09-22 第二轮）

> 上一轮的原内容：用户报「外观设置打不开」。根因不是 bug —— `AppearanceSettingsDialog`
> 的实现是**通过 Tauri `WebviewWindow` 创建一个 OS 级独立窗口**（加载 `appearance.html`），
> **Android 没有多窗口能力**，所以点了不会有任何反应。当时保留了菜单项但只给提示，记为待办。
> **本轮把待办做完了。**

**做法：不重写那 1421 行，给上游面板加一层「宿主适配」**

`AppearanceWindow.tsx` 与主窗口的全部耦合只有 4 处，且都是"关自己窗口 / 发跨窗口事件"：

| 原调用 | 独立窗口下的语义 | 嵌入模式下改为 |
| :--- | :--- | :--- |
| `getCurrentWindow().close()` | 关掉面板自己的窗口 | `host.close()` → `onOpenChange(false)` |
| `emit("appearance-applied")` | 通知主窗口重读 localStorage | `host.applied()` → 同树直接重读 |
| `emit("appearance-preview", p)` | 把预览值推给主窗口 | `host.preview(p)` → 直接写 `documentElement` |
| `emit("appearance-reverted")` | 通知主窗口回滚 | `host.reverted()` |

于是引入**模块级单例槽** `activeHost`（同一时刻只可能有一个外观面板存活，语义精确）：
4 个模块级辅助函数先看槽里有没有宿主，没有才走原 Tauri 路径 ⇒ **桌面端行为一行不变**。
`AppearanceSettingsDialog` 加 `embedded` 分支（判据：UA 含 `Android`；创建窗口失败也会
`catch` 回退到它），渲染近全屏的 Radix `Dialog.Content` 包同款面板。

**两个必须踩过的坑**

1. **`Dialog.Content` 不能只写 `width:100vw / height:100dvh`**：Radix Themes 自带
   "居中定位 + 内边距 + max-height"，实测 800×1176 视口下面板只量到 `784×1154` 且
   **底部溢出 24px** ⇒ 最下面的「关闭 / 应用」被推出视口，**人点不到、探针也点不到**。
   改成 `position: fixed; inset: 0; transform: none` 才严格铺满。
2. **预览绝不能走 `applySettings`**：它会写 localStorage 主键，于是「关闭」时
   `loadAppearance()` 读到的已经是预览值 ⇒ **回滚变成空操作**。预览改走
   `setMode / setAccentColor / ...` 这些只 setState、不落盘的 setter。
   另外面板**挂载首帧就会发一次 preview**（此时 colors 为空），若按"缺谁清谁"处理，
   打开面板的瞬间会把用户已有的自定义配色整片抹掉 ⇒ 颜色要「先按当前主题铺底、再叠预览色」。

**验收（`scripts/_probe-appearance.mjs`，CDP 量化断言）**

| 形态 | 视口 | 结果 |
| :--- | :--- | :--- |
| 平板 | 800×1176 | 面板 `rect=2,3 796×1171` 铺满；①打开 ②排版 ③Tab ④预览 ⑤回滚 ⑥落盘 **全通过** |
| 手机 | 360×731 | 面板 `rect=1,1 358×729` 铺满；Tab 与「关闭/应用」都在视口内，内容区横向溢出 **0px** |

**触摸目标**：面板是按鼠标口径排的，原样嵌入后实测面板内 **51 个可点元素里 46 个 < 40px**
（分段 Tab 高 29、导入/导出高 31、调色板色块 24×24）。在 `index.css` 里按
`[data-hs-appearance-root="embedded"]` 收口抬到 40（色块取 32 —— 密排网格，理由见 CSS 注释）；
**刻意不用媒体查询**：800px 宽的平板同样需要抬起命中区，而 599px 断点会漏掉它。

## 13. 平板的功能缺口：👁 面板没有入口（2026-09-22）

### 13.1 发现

phone 的「参数工具行」只渲染在 **phone + params 页签**（`App.tsx` 里 `mobileTab === "params"`），
而第 12 节把 **选择/绘制/眼睛 从底栏整体搬走** ⇒ 实测平板：

| 项 | 实测（800×1176）|
| :--- | :--- |
| `[aria-label="参数工具行"]` | **0**（不渲染）|
| `.param-pill`（参数切换）| 6 个（音高/共振峰/气声/张力/音量/声像）—— 够得着 ✓ |
| `.hs-param-head` | 500×28（常显）✓ |
| `.hs-param-toolbar` | 751×32（常显）✓ |
| 覆盖层 / 参数与覆盖层的按钮 | **0**（`eyeBtn: 0`）|

⇒ 平板**并非整体回归**（参数切换、同步位置、拖动方向、参考轨道组、导入 MIDI 都在常显的
`.hs-param-head` / `.hs-param-toolbar` 里），**但 👁 面板独有的三项彻底没有入口**：

1. **覆盖层总开关**（全部副参数覆盖层的显隐）
2. **单项曲线显隐**（音高/共振峰/气声/张力/音量/声像 逐条显隐）
3. **气声 开启/关闭**

> why：这三项只存在于 `VerticalDualPanel`（原 `MobileBottomBar` 里的 👁 浮层），
> 与桌面 `ActionBar` 的两个眼睛图标是同一功能 —— 而平板 800px 下那两个图标在工具栏的
> 横向滚动区之外（`docs/04 §3.3` 已记录过这一点），所以**两条路都够不着**。

### 13.2 修法：把 👁 放到平板底栏（∧ 旁边）

`MobileBottomBar({ showEye })`，`App.tsx` 传 `showEye={!isPhone}`：

- 位置与 phone 的参数工具行一致 —— 都是「折叠类开关」，与 ∧ 同族；
- 复用**同一个** `VerticalDualPanel`（自带镜像订阅 `hs-param-ui-state` / 回写
  `hs-set-secondary-param` / `hs-set-static-param`），不新建一套；
- 面板本身是 `absolute; bottom: 100%`（向上展开），底栏是它的天然位置；
- phone 不受影响（`showEye=false`，👁 仍在参数工具行）。

**为什么不在平板也渲染整个「参数工具行」**：`选择/绘制/∨` 在平板是**冗余**的 ——
`.hs-param-head` / `.hs-param-toolbar` 常显，选择/绘制已在其中，而 ∨ 的全部内容
（同步位置/拖动方向/音高吸附/锁定/参考轨道组/导入 MIDI/平滑度）也已在屏上；
∨ 的浮层 CSS（`body[data-hs-param-menu]`）**只写在 `@media (max-width:599px)` 里**，
平板点了不会有任何反应 —— 那才是真 bug。平板只需要补 👁 这一项。

### 13.3 平板的 `tooSmall 59`：一次口径澄清（未改）

平板审计长期报 `tooSmall 59`，明细全部是 ActionBar 的密排控件：

| 形态 | 命中区（审计实测）|
| :--- | :--- |
| `button.rt-BaseButton` 图标按钮 | 视觉 24×36 → **命中区 34×40** |
| `input.rt-TextFieldInput` | 58×36 / 40×36 |
| `button.rt-SelectTrigger` | 48×36 / 66×36 |

两条口径不一致，值得摊开：

- `docs/04 §5` 引 Material ⇒ **44×44**；
- **项目自己的决策**（`docs/01`，用户拍板）⇒「底栏按钮视觉 28px、**命中区 40px**」。

按 40 的口径，上面这些「高度 36 / 命中 40」的对象里，**只有宽度方向仍不足**
（图标按钮命中 34 < 40；输入框/下拉是 w≥40 但 h=37）。要真正到 44×44 **只能重设计工具栏**
（减少按钮数或加大间距）—— 硬把 `::after` 横向扩到 ±10px 会让相邻按钮命中区互相覆盖、
偷走隔壁的点击，反而更糟（`docs/04 §7` 已记）。

**本轮不动**：这是「设计取舍」不是「实现缺陷」，且平板是次要形态；留给用户决定
（①接受 40px 标准 ②减按钮 ③把低频开关收进 ∧ 同级菜单）。
