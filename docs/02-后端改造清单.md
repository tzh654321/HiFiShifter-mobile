> 目标：让 `cargo build --target aarch64-linux-android --no-default-features --features onnx` 通过并可用。
> 基线：`develop` 分支（`backend/src-tauri/`，Rust 71,453 行）

## 1. 依赖逐条判定

### 1.1 平台专属依赖

| 依赖 | 现状 | Android 处置 |
| :--- | :--- | :--- |
| `clipboard-win = "5"` | `[target.'cfg(windows)']` | 删除该 target 块；新增 Android 走 `tauri-plugin-clipboard-manager` |
| `windows-core = "0.58"` / `windows = "0.58"`（14 个 Win32 feature） | Windows + DirectML 用 | 保留在 windows 块内不动，Android target 自动不编译 |
| `libc` | win/mac/unix 三处 | 保留（Android 属 `cfg(unix)`，会有 Linux 分支的 `libc` 依赖，但 `xcb` / `wl-clipboard-rs` 要去掉） |
| `xcb` / `wl-clipboard-rs` | `cfg(target_os = "linux")` | **必须确认 Android target 不会命中这个 cfg**。`aarch64-linux-android` 的 `target_os` 是 `android` 而非 `linux`，理论上安全；但应在 Android 块里显式加 `[target.'cfg(target_os = "android")']` 覆盖，避免误编译 |
| `objc2-*` | macOS | 不动 |
| `rfd = "0.15"` | 全平台 | **需评估**：rfd 在 Android 上无实现。推荐改为 `tauri-plugin-dialog`；若坚持用 rfd，需要给 Android 写一个 `pick_file` 的桩（走 SAF） |

### 1.2 需要"给 Android 换 EP"的依赖

现有 5 个 `ort` 目标块（Windows=DirectML / Linux x64=WebGPU / Linux aarch64=CPU / macOS ARM=CoreML+WebGPU / macOS Intel=tract），**没有 Android 块**。需要新增：

```toml
# Android —— 用 load-dynamic，so 由 jniLibs 提供；EP 走 NNAPI，失败自动回落 CPU
[target.'cfg(target_os = "android")'.dependencies]
ort = { version = "2.0.0-rc.13", optional = true, default-features = false,
        features = ["std", "ndarray", "tls-native", "load-dynamic"] }
```

要点：
- **不要** `download-binaries`（Android 的预编译产物不由 pykeio 的下载通道提供）。
- **不要** `copy-dylibs`（那是把 dylib 复制到 target 目录，Android 需要的是打进 APK 的 jniLibs）。
- `nnapi` 是否启用留给 §4 的探针决定。

### 1.3 feature 默认值必须改

```toml
# 现在
default = ["onnx", "vslib"]
# 改为（vslib 是 Windows DLL，永远不该进 Android 构建）
default = ["onnx", "vslib"]           # 保持桌面默认不变
```

**策略**：不改 `default`，而是**在 Android 构建命令里显式 `--no-default-features --features onnx`**（与上游给 Linux AppImage 的做法完全一致，见 README "Linux AppImage 构建" 一节）。这样零侵入上游。

> 但要注意：`lib.rs:123` 等处是 `#[cfg(all(feature = "vslib", target_os = "windows"))]`，已经双保险，所以 `vslib` feature 即使被打开也不会在 Android 上编译出 Windows 代码。真正要小心的是 `renderer/mod.rs:17,35` 同样写了双条件——已安全。

### 1.4 音频后端

```toml
# 现在
cpal = "0.15"

# Android 需要（社区已验证的写法）
[target.'cfg(target_os = "android")'.dependencies]
cpal = { version = "0.15.3", default-features = false, features = ["oboe-shared-stdcxx"] }
```

原因：Android 的 Oboe 后端是 C++ 实现，默认链接 `libc++_shared.so`，若 APK 里没有这个 so 就会 `dlopen failed`。加上 `oboe-shared-stdcxx` 让 cpal 静态链接 stdc++。

**备选**：升级 cpal 到 0.16+（Android 后端换成 AAudio，不再有 C++ 运行时依赖）。这需要在 `Cargo.lock` 层面评估与其它依赖的兼容性。

### 2.3 `build.rs` 改造（编译期原生库）

`build.rs` 目前无条件编译 4 个原生库：`build_world_static()` / `build_signalsmith_stretch()` / `build_vslib()` / `build_soundtouch()`，且其中有大量 Windows 专属逻辑（comctl32 delay-load、DirectML.dll 拷贝）与 macOS 专属逻辑（dylib staging、CoreML 模型改写）。

Android 需要：
1. **`build_vslib()` 在 Android 上直接跳过**（Windows DLL）。
2. **`build_soundtouch()`**：现在是 `cc` 编译成 `SoundTouchDLL.dll/.so/.dylib`。Android 需要编译成 `libSoundTouchDLL.so` 并放进 `jniLibs/arm64-v8a/`。需要给 `cc::Build` 设置正确的 `ANDROID_ABI`/`ANDROID_PLATFORM`，以及 C++ 标准库（`cpp_link_stdlib("c++_shared")` 或 static）。
3. **`build_world_static()`**：WORLD 是纯 C++ 静态库，理论可交叉编译，需验证 `cc` 对 `aarch64-linux-android` 的 NDK clang 探测。
4. **`build_signalsmith_stretch()`**：header-only + C++，同样需要 NDK clang。
5. **`create_vslib_placeholder()` / `copy_directml_dll()` / `stage_ort_macos_dylibs()` / `generate_coreml_model_variant()`**：前两个已有 `cfg!(target_os=...)` 守卫，Android 自动跳过；后两个同理。**但 `create_vslib_placeholder()` 的守卫是 `if !cfg!(target_os = "windows") { return; }`，Android 安全**。
6. **`build_frontend()`**：Android 构建也要构建前端，保留。
7. 资源校验：`tauri_build::build()` 会校验 `tauri.conf.json` 声明的 resources 是否存在。Android 上 `resources/models/nsf_hifigan/config.json` 等小文件可继续走 resources；**184 MB 的 `.onnx` 建议改走 Android assets 而不是 tauri resources**（见 §3）。

## 3. 资源与模型加载（本方案最需要重做的部分）

### 3.1 现状

```rust
// lib.rs:230-247
if let Ok(res_dir) = app.path().resource_dir() {
    let p = res_dir.join("models").join("fcpe").join("fcpe.onnx");
    ...
}
```

`resource_dir()` 在 Android 上返回 `asset://localhost/` → `res_dir.join(...)` 得到的是 URI，**`std::fs::read` 必然失败**。

### 3.2 目标设计

```
首次启动:
  1. 读 app_data_dir()/models/.version  → 与内置版本号比对
  2. 若不一致: 从 APK assets 流式拷贝 models/** 到 app_data_dir()/models/
     - 分文件、带进度事件（前端已有 ProgressBar / PitchAnalysisProgressBar 组件可复用）
     - 拷完写 .version
  3. ort 从 app_data_dir()/models/ 加载
```

模型路径统一收口到一个函数：

```rust
pub fn model_path(app: &AppHandle, rel: &str) -> Result<PathBuf, String> {
    #[cfg(target_os = "android")]
    { return Ok(app.path().app_data_dir()?.join("models").join(rel)); }
    #[cfg(not(target_os = "android"))]
    { /* 保持上游 dev / resource_dir 双路逻辑不变 */ }
}
```

然后把 `lib.rs:180 / 230 / 240 / 247`、`fcpe_onnx.rs:77`、`hnsep_onnx.rs:59`、`nsf_hifigan_onnx.rs:220` 这几处硬编码的 `CARGO_MANIFEST_DIR` / `resource_dir()` 全改为调 `model_path()`。

> **注意 `nsf_hifigan_onnx.rs:220` 的注释**已经点明这个坑：*"CARGO_MANIFEST_DIR 在发布构建中指向构建机器的路径，在用户机器上不存在"* —— 上游已经吃过一次亏，Android 上会再吃一次，所以直接收口是必要的重构而不只是加分支。

### 3.3 可选模型与降级

- `hnsep.onnx`（88 MB）缺失 → 禁用"气声/张力"编辑。上游 `pitch_clip.rs:397/670`、`pitch_analysis/analysis.rs:1288` 已有 `is_available()` 判空分支，前端需相应地把参数面板的"气声/张力"置灰并给出提示。
- `fcpe.onnx`（41 MB）缺失 → 音高分析退回 WORLD Harvest/DIO。`analysis.rs:421` 已有 `infer_f0_hz` 的调用点，需要加降级路径。

**建议**：APK 里只内置 `nsf_hifigan`（54 MB，核心声码器）+ `config.json`；`hnsep` 与 `fcpe` 做成"设置页可下载/可导入"的可选包。这样基础 APK 从 ~250 MB 降到 ~90 MB 量级。

## 5. 一个容易被忽略的点：线程与后台

- `audio_engine` 用 `std::thread` 起独立线程播放；Android 上 App 退到后台后，进程可能被冻结（Doze / 后台限制），音频线程与推理线程会被挂起。
- 上游的离线渲染模型（"对每个音频块处理、渲染、缓存"）天然适合 Android：
  - **前台播放**：正常。
  - **后台**：需要 `MediaSession`/前台服务才能继续，成本高。**建议第一版不做后台播放**，退后台即暂停。
- 长耗时任务（音高分析、hnsep 分离）必须有：
  - 进度事件（上游已有 `pitch_progress` / `emit("track_meter")` 等事件通道）
  - **可取消**（Android 用户会强退，且低端机可能 OOM）
  - 唤醒锁策略：屏幕熄灭时 CPU 可能降频，长任务建议加 `WakeLock`（可选）

### 6.3 未预判的两个"环境级"阻塞（都不在上游代码里）

| 现象 | 根因 | 处置 |
| :--- | :--- | :--- |
| `fdk-aac-sys`: `'log/log.h' file not found` | `lpp_tran.cpp` 在 `#ifdef __ANDROID__` 下无条件 include AOSP 的 `log/log.h`，而 **NDK 的 sysroot 里根本没有 `log/` 目录**（只有 `android/log.h`） | 新增 `android/shim/fdk-aac-log/log/log.h`，只通过 `-I` 注入 |
| 同上，第二层：`android_errorWriteLog` 未声明 | 那是 **AOSP 私有 API，NDK 稳定 ABI 不导出**（fdk-aac 只用它做 CVE 标记，不参与音频计算） | 在同一 shim 里给 no-op 实现 |
| `opusic-sys`: `is cmake not installed?` | **本机没装 cmake**（SDK 默认不带） | `sdkmanager --install "cmake;3.22.1"` |
| SoundTouch configure: `Failed to run MSBuild command ... get the value of VCTargetsPath: Access violation` | **cmake 的生成器在加载 toolchain file 之前就已定下来**：Windows 上默认选 "Visual Studio 17 2022"，而 VS 生成器强制用 MSVC、会完全忽略 toolchain 里的 clang。所以 `-DCMAKE_TOOLCHAIN_FILE=` 单独指定是**不够的** | `build.rs` 里补 `-G Ninja`（SDK 的 cmake 包自带 `ninja.exe`，与 `cmake.exe` 同目录，只要 cmake 在 PATH 里就能找到）|

> ⚠️ 附一个**极其隐蔽**的坑：`CFLAGS` 里塞的路径必须是 **Windows 形式**（`C:/...`），
> 因为 `clang.exe` 是原生程序、不认 MSYS 路径 `/c/...`。
> 传错形式时 clang 会**静默忽略**那个 `-I`，报错依旧停在 `'log/log.h' file not found`，
> 看起来像"shim 没生效"，实际是路径形式不对。

### 6.4 18 个 Tauri 桌面窗口 API 错误（方案期的盲区）

Tauri 把 `set_title` / `set_size` / `set_position` / `set_fullscreen` /
`maximize` / `close` 标记为 **desktop-only**，移动端的 `WebviewWindow` /
`Window` 上没有这些方法：

| 方法 | 次数 | 分布 |
| :--- | ---: | :--- |
| `set_title` | 10 | `project.rs`(5) / `project_import.rs` / `reaper.rs` / `vocalshifter.rs` / `state.rs` / +1 |
| `set_size` | 3 | `lib.rs`（窗口尺寸记忆恢复）|
| `set_position` | 2 | `lib.rs`（窗口位置记忆恢复）|
| `set_fullscreen` / `maximize` | 3 | `lib.rs`（全屏/最大化状态恢复）|
| `close` | 1 | `project.rs` |

**处置（`src/platform/window.rs`）**：提供**同名同签名**的扩展 trait
`DesktopWindowCompat`，移动端实现为 no-op。这样：

- 18 处调用点**一行都不用改**（全是 `let _ = win.set_xxx(...)`，返回值本来就被忽略）；
- 桌面端**固有方法优先**，trait 不会被选中，行为与上游完全一致；
- 这些功能在移动端本来就该由 OS 提供（标题、关闭手势）或根本无意义（尺寸/位置/最大化）。

> 用 no-op 而不是返回 `unsupported`：这 18 处的返回值没有任何调用方会读，
> 返回 `Err` 只会污染日志。

### 6.5 一个上游自身的隐患（本次不受影响，但值得上报）

`build.rs` 里有两套平台判断，语义**不同**：

- `let target_os = std::env::var("CARGO_CFG_TARGET_OS")...` —— **目标** OS ✓
- `if !cfg!(target_os = "windows") { return; }`（`copy_directml_dll` /
  `stage_ort_macos_dylibs` / `create_vslib_placeholder`）—— **宿主** OS ✗

交叉编译时两者不一致：从 Windows 交叉编译到 Android，`cfg!(target_os = "windows")`
为真，于是 `copy_directml_dll()` 会真的去执行（后果只是找不到文件打条 warning），
而 `stage_ort_macos_dylibs()` 会正确地 return。

我们的 `build_soundtouch()` 改动**用的是前者（目标的 `CARGO_CFG_TARGET_OS`）**，
所以是对的。建议向上游提 issue 统一成 `CARGO_CFG_TARGET_OS`。

### 6.7 ⚠️ 一个会「掩盖问题」的构建缓存行为

`build.rs` 用 `std::env::var("HIFISHIFTER_SKIP_NATIVE_BUILD")` 控制是否构建
WORLD / Signalsmith / SoundTouch，但**没有声明
`cargo:rerun-if-env-changed=HIFISHIFTER_SKIP_NATIVE_BUILD`**。

后果：cargo 不追踪这个环境变量，**改它的值不会让 build script 重跑**。
实测踩到：先用 `SKIP_NATIVE=1` 跑过一次 check（build script 输出被缓存），
然后不设该变量再跑，8.45 秒就 `exit=0` 了 —— 看起来"native 也过了"，
其实 build script **根本没执行**，日志里连 `[soundtouch] starting ...` 都没有。

**验证方法**：看日志里有没有 `[soundtouch] starting build_soundtouch...`；
或 `touch backend/src-tauri/build.rs` 强制重跑。

补一句给上游的建议：这个开关应该配 `cargo:rerun-if-env-changed`，
否则 CI 里 "先跑快速检查、再跑完整构建" 的流水线会**静默跳过原生库构建**。

### 7.1 ✅ 模型/资源路径收口已实现（`src/platform/resources.rs`）

第 3 节预判的方案是对的，实现比预想还干净 —— 因为上游**把三个模型的路径

### 7.2 🔴 新发现：移动端**根本没有 logger**

`logging::init_logging()` **只在 `main.rs` 里调用**：

```
src/main.rs:32:  backend_lib::logging::init_logging(...)
```

而 Android 的入口是 `lib.rs`（经 `mobile_entry_point`）—— `main.rs` 不参与。
后果：**移动端一个 logger 都没装**，`log::info!/warn!/error!` 全部**被静默丢弃**
（`log` 门面在没有 logger 时就是空操作）。另外 `logging::default_log_dir()`
也**没有 Android 分支**（只有 windows / macos / unix）。

实测症状：我们加的 `log::info!("[resources] 模型就绪…")` 在 logcat 里搜不到，
上游关于模型预热的日志也一条看不到 —— 排查 M2/M3 问题会**完全失明**。

**已补 `src/platform/logging.rs`（Android 专用）**，两条通道：

1. **logcat**（tag `HiFiShifter`，直接用 `__android_log_write`，`liblog.so`）；
2. **落盘** `<app_log_dir>/android.log`（超过 4 MB 在启动时截断），
   用 `adb exec-out run-as <pkg> cat logs/android.log` 取全文。

两条都要的理由：logcat 是**环形 buffer 且有损**（本机有后台应用每 200 ms 刷屏，
很快把我们的行冲掉）；落盘不受影响。`scripts/run-app.sh` 已按这个优先级实现取日志。

调用点是 `setup()` 的**第一件事** —— 必须早于 `ensure_ndk_context()`，
否则连 ndk_context 的成功/失败都看不到。

`platform/resources.rs` 的 `RawAsset::open` 原文是：

```rust
(!ptr.is_null()).then_some(Self { ptr })   // ← 崩
```

`AAssetManager_open` 找不到资产时返回空指针，`Self { ptr }` **仍被构造出来**，

### 7.6 🔴 顺带抓到一个**真实的运行时缺陷**：前端 `ResizeObserver` 反馈环

日志里刷得最多的是同一个错误：

```
[ERROR] commands::diagnostics: [frontend] Uncaught error:
  ResizeObserver loop completed with undelivered notifications.
  | detail: http://tauri.localhost/:0:0
```

**准确速率（实测）**：先清空日志文件 → 重启应用 → 卡 30 秒窗口
→ **832 条 / 30 秒 = 27.7 条/秒**。

> ⚠️ 记一个测量陷阱：日志文件是**跨运行追加**的（只有超过 4 MB 才在启动时截断），
> 所以"整份文件里的条数"**不能**当速率用 —— 必须清空后开固定窗口。
> 我第一次就差点把累计条数当成 48 条/秒报出去。

**为什么值得记**：这正是「桌面布局被硬塞进 360×800」的直接后果 ——
`ResizeObserver` 里同步改了尺寸 → 触发下一轮 resize → 再次回调，形成自持的反馈环。
在桌面宽屏下这个环是收敛的（有足够空间让尺寸稳定），压到手机宽度后不收敛了。

它同时说明两件事：

- **`docs/04` 的三套布局不是"优化"，是修 bug** —— 这个环本身就在持续烧 CPU 与电量
  （27.7 次/秒的错误构造 + 日志写入 + WebView 跨进程调用）；
- 后面做移动布局时，**`docs/08` 里"提交必须同步、且 `scrollLeft` 与 `pxPerSec`
  同帧送达"那条契约**要一并检查：尺寸类观察者（ResizeObserver）与视口写入
  若互相触发，就是同一个环的另一个形态。

> 排查建议：在 `docs/04` 的实现阶段，先给 `ResizeObserver` 回调加"本轮已派发"的
> 去抖/短路（只在尺寸**实际变化**时写入），再用同一份日志验证错误数降到 0。
> 这条比"看起来排版对不对"更客观，可以直接当验收指标。

> 顺带：这条也说明**日志后端不能省**。没有它，这个 27.7 次/秒的环在外部完全不可见。

### 7.7 ⏳ 新发现：三个模型 session 是**全局串行**建的

日志里能直接读出会话构建时序（模拟器 x86_64）。**冷、热两次差别很大**：

| 场景 | fcpe | pc_nsf_hifigan | hnsep | 第 3 个模型拿锁等待 |
| :--- | ---: | ---: | ---: | ---: |
| **冷启动**（首次运行，含 184 MB 模型物化） | — | 3566 ms | 10136 ms | **18.37 s** |
| **热启动**（模型已在私有目录） | 550 ms | 946 ms | 2137 ms | **2.53 s** |

**机制**：`vocoder_ort_session` 用一把**全局锁**串行化 session 构建：

```
ort_session: waiting for the global session build lock (10.03s elapsed) — another build is in progress
ort_session: acquired the global session build lock after 2.526450536s (a build was in progress)
```

这是上游刻意的（避免多个大模型同时申请内存把进程打爆，与 `docs/10` 里
"RSS 与块长强相关"是同一类考虑）。

**结论（比初看乐观）**：

- **热启动 ~2.5 秒**把三个 session 建完 —— 移动端可接受，
  「懒建 / 并行」这类优化**暂时不需要做**。
- **冷启动那 18.4 秒**才是要关注的：它和「首次物化 184 MB 模型」是同一时刻发生的
  （`setup()` 里同步拷贝 + 后台预热线程建 session）。两者叠加会让**首次启动**明显卡。
  → 这一段的体验处理（轻量 splash / 进度提示）应放在**首次启动**路径上，
  而不是每一次启动。
- 真机数字还需复测（模拟器是软件 CPU + 无大小核调度，会夸大）。
  日志文件里 `commit_ms=` 与拿锁等待时长都能直接读，**不用额外埋点**。

> 顺带一个可复用的观测手段：`docs/10-应用运行时日志-20260918.log` 就是
> 「清空日志 → 重启 → 固定 30 秒窗口 → `run-as` 取回」的产物，
> 折叠重复行后只有 29 行却包含全部关键时序。**做性能对比时用这个格式，不要看累计文件。**
