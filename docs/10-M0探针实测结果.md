## 1. 一句话结论

**Tauri 2 走 Android 是可行的，四条卡点里三条已实测打通（模拟器 + 真机 arm64 双端复跑），一条（音频）已找到并修好了真正的阻塞原因。真机数字见 §9。**

但**最关键的一条和原方案预判的完全不同**：

> 原方案认为音频的头号风险是 `cpal/Oboe 需要 libc++_shared.so`。
> **实际的头号阻塞是 `ndk_context` 从未被初始化，而 cpal 强依赖它、并且会 panic。**
> `libc++_shared.so` 那条 Tauri 已经自动处理了（见 §5.7）。

## 3. 逐探针结果

### 探针 0 · 环境与路径 ✅ 全部符合预期

```
target_os      = android
target_arch    = x86_64
编译目标        = x86_64-linux-android
当前工作目录    = Ok("/")                      ← Android 上进程 cwd 就是根目录
current_exe    = Ok("/system/bin/app_process64")  ← 不是我们的 .so，别用它找路径
resource_dir        = asset://localhost/       ← ★ 不是文件系统路径！
app_data_dir        = /data/user/0/<pkg>       ← 真实可写路径 ✓
app_local_data_dir  = /data/user/0/<pkg>
app_cache_dir       = /data/user/0/<pkg>/cache
app_config_dir      = /data/user/0/<pkg>
temp_dir            = /data/user/0/<pkg>/cache
```

**这条验证了 `docs/02` 的核心假设**：`resource_dir()` 返回 `asset://localhost/`，
所以 ort 读不到模型，必须先把模型从 APK assets 拷到 `app_data_dir()`。

⚠️ 另外两个反直觉点（新发现）：
- `std::env::current_dir()` 在 Android 上是 `/`，**不能用来定位资源**。
- `std::env::current_exe()` 是 `/system/bin/app_process64`，**也不是我们的库路径**——
  想拿 native 库目录要用 JNI 取 `ApplicationInfo.nativeLibraryDir`（探针实测可行）。

### 探针 2 · cpal / Oboe 输出 ✅ 出声成功

```
host.id = Oboe                                  ← Android 后端正确生效
default_output_device 的名称 = Ok("default")
default_output_config = 44100 Hz / 2 声道 / F32  ← 不再 panic（修复前必 panic）
supported_output_configs 共 12 项
   支持: 1 声道 / I16 / 5512 / 8000 / 11025 / 16000 / 22050 / 32000 /
                        44100 / 48000 / 64000 / 88200 / 96000 / 176400 Hz
开始生成 132300 帧 / 2 声道 / 3 秒的双音（440→660 Hz 交替）
✅ 流建立并播放 3 秒；回调共输出 276828 个样本（期望约 264600）
```

**回调真的在跑**（276828 > 264600，因为 stream 一直放到 drop 才停）。

⚠️ `supported_output_configs` 那 12 项**都是 1 声道 / I16**，而 `default_output_config`
给的是 44100 / 2ch / F32 —— 两者并不一致。原因在 cpal 源码里很清楚：
`Device(None)` 时它调用 `default_supported_configs()`，那是**暴力枚举出来的候选表**
（采样率 × 声道掩码 × 格式，逐个调 `getMinBufferSize` 过滤），
**不是设备的真实能力**。真正的能力要枚举到具体 `AudioDeviceInfo` 才有。

→ **对移植的影响**：上游 `audio_engine` 若依赖 `supported_output_configs()` 做协商，
在 Android 上拿到的是这份"猜测表"而不是真实能力，需要改成
用 Oboe 的设备枚举 + `default_output_config()`，或直接以 `default_output_config()` 为准。

## 4. 🔴 头号发现：Tauri 栈从不初始化 `ndk_context`，而 cpal 强依赖它

### 4.1 现象

第一版探针跑到探针 1 就整个线程 panic，后面 4 个探针一个都没跑：

```
thread '<unnamed>' (3229) panicked at ndk-context-0.1.1\src\lib.rs:72:30:
android context was not initialized
```

### 4.2 证据链（全部来自本地 registry 源码，非推测）

| 事实 | 位置 |
| :--- | :--- |
| `android_context()` 未初始化时**直接 panic** | `ndk-context-0.1.1/src/lib.rs:72` `ANDROID_CONTEXT.expect("android context was not initialized")` |
| cpal 的 Oboe 后端**直接调它** | `cpal-0.15.3/src/host/oboe/android_media.rs:18` |
| cpal 枚举设备也走它 | `cpal-0.15.3/src/host/oboe/mod.rs:65` `oboe::AudioDeviceInfo::request(...)` |
| oboe-rs 的 java_interface 也走它 | `oboe-0.6.1/src/java_interface/utils.rs:14` |
| **tauri 不初始化它** | `grep -rn initialize_android_context tauri-2.11.5/src` → 空 |
| **tauri-runtime-wry 不初始化** | 同上 → 空 |
| **wry 不初始化** | `wry-0.55.1/src` → 空 |
| **tao 不初始化** | `tao-0.35.3/src` → 空（`android_binding!` 只管自己的 activity 生命周期） |
| `run_on_android_context` **拿不到** | 它挂在 `RuntimeOrDispatch` 上，而后者在 `pub(crate) mod sealed` 里 |
| tao/wry **不公开** Activity | 只有 `pub(crate) static ACTIVITY_CREATED_SENDERS`、`pub fn activity_window_manager`（在私有 `platform_impl` 内） |

### 4.3 触发路径（会 panic 的调用）

```
host.devices()
  └─ oboe::AudioDeviceInfo::request() → java_interface → ndk_context::android_context() → panic

device.default_output_config()
  └─ device.supported_output_configs()
       └─ default_supported_configs()          ← Device(None) 时走这条
            └─ buffer_size_range_for_params() → get_audio_track_min_buffer_size()
                 └─ android_media::with_attached() → ndk_context::android_context() → panic
```

**HiFiShifter 的 `audio_engine` 一定要查设备能力 → 这是硬阻塞，必须修。**

### 4.4 解法（已实测通过，**零 Kotlin 改动**）

```rust
// ① 自己抓 JavaVM —— tao / wry / jni 都**没有**占用 JNI_OnLoad 这个符号
static JVM: AtomicPtr<c_void> = AtomicPtr::new(std::ptr::null_mut());

#[no_mangle]
pub extern "system" fn JNI_OnLoad(vm: *mut c_void, _reserved: *mut c_void) -> i32 {
    JVM.store(vm, Ordering::SeqCst);
    0x0001_0006 // JNI_VERSION_1_6 —— 不返回版本号 JVM 会认为加载失败
}

// ② 用 ActivityThread.currentApplication() 取一个 Context
let vm_raw = JVM.load(Ordering::SeqCst);
let vm  = unsafe { jni::JavaVM::from_raw(vm_raw.cast()) }?;
let mut env = vm.attach_current_thread()?;
let at  = env.find_class("android/app/ActivityThread")?;
let app = env.call_static_method(
              at, "currentApplication", "()Landroid/app/Application;", &[])?.l()?;

// ③ ⚠️ 必须转成全局引用！
//    本地引用会随 attach guard 析构（DetachCurrentThread）一起失效，
//    而 ndk_context 要长期持有这个 jobject。
let app_global = env.new_global_ref(&app)?;
let ctx_ptr: *mut c_void = app_global.as_obj().as_raw().cast();
std::mem::forget(app_global);   // 故意泄漏，ndk_context 持有到进程结束

unsafe { ndk_context::initialize_android_context(vm_raw, ctx_ptr) };
```

**实测结果**：初始化前 `可用性 = false` → 初始化后 `context() = 0x330a`（非空），
随后 cpal 的 `supported_output_configs()` 正常返回 12 项、`default_output_config`
= 44100/2ch/F32，**不再 panic**。

**风险与退路**：`android.app.ActivityThread` 属于 Android **隐藏 API**，
targetSdk ≥ 28 时理论上会被 non-SDK 接口限制拦截（表现为 `NoSuchMethodError`）。
**实测在 API 35 + targetSdk 36 下没有被拦。** 若将来某版本被拦，退路是：
在 `gen/android` 的 Kotlin `MainActivity` 里调一个 `#[no_mangle]` 的 Rust 函数，
把 `Activity` 直接传进来（Tauri 允许改生成出来的 Android 工程）。

> **这条对上游改造的具体落点**：应当封装成
> `backend/src-tauri/src/platform/android_context.rs`，
> 在 `tauri::Builder::setup` 里最先调用一次，**在任何 cpal 调用之前**。

## 5. 其他实测发现

### 5.1 ⚠️ `load-dynamic` 下**绝不能直接引用 `ort::sys::*` 的符号**

我在探针里加了 ONNX Runtime 版本查询，随手写了 `ort::sys::OrtGetApiBase()`。结果：

```
dlopen failed: cannot locate symbol "OrtGetApiBase"
    referenced by ".../libm0_probe_lib.so"
→ java.lang.UnsatisfiedLinkError（FATAL，App 在任何 Rust 代码跑起来之前就死）
```

原因：`load-dynamic` 模式下 ORT 是运行时 dlopen 的，**编译期不链接**。
任何对 `ort::sys::Ort*` 函数/静态量的直接引用都会在我们的 `.so` 里留下
**未定义符号**，`dlopen` 阶段就失败。

**正确做法**：走 `ort::api()` / `ort::info()`——它们内部用 `ortsys!` 宏做运行时解析。

- 版本信息用 `ort::info()`（返回 ORT build info 字符串）。
- 上游 `backend/src-tauri/src` 里若有直接引用 `ort::sys` 的地方，**都要改**。

**已加构建守卫**：`scripts/run-probe.sh` 在构建后会用 `llvm-readelf` 检查
`libm0_probe_lib.so` 里有没有未定义的 `Ort*` 符号，有就直接报错、不装机。

### 5.2 `eprintln!` 在 Android 上会进 logcat，但**会丢行**

实测 `eprintln!` 走 tag `RustStdoutRerror`（实际是 `RustStdoutStderr`），
但探针开头 6 行丢了；而自建 liblog 通道（tag `PROBE`）**一行不丢**。
→ 移植后诊断日志**必须**走 liblog（`__android_log_write`，`#[link(name="log")]`）。

### 5.3 `ndk 0.9` 没有 `AssetManager::from_java`

`ndk-0.9.0/src/asset.rs` 只有 `from_ptr(NonNull<ndk_sys::AAssetManager>)` / `open` / `open_dir`；
**没有 `from_java`**，而 ndk 0.9 又没有公开重导出 `ndk_sys`（无法命名那个指针类型而不锁死版本）。

→ **直接声明 `AAsset*` 的 C FFI**（符号在 **libandroid.so**，NDK sysroot 里两个 ABI 都有 stub）：

```rust
#[link(name = "android")]
extern "C" {
    fn AAssetManager_fromJava(env: *mut c_void, am: *mut c_void) -> *mut c_void;
    fn AAssetManager_open(mgr: *mut c_void, name: *const c_char, mode: c_int) -> *mut c_void;
    fn AAsset_getLength64(a: *mut c_void) -> i64;
    fn AAsset_read(a: *mut c_void, buf: *mut c_void, n: usize) -> c_int;
    fn AAsset_close(a: *mut c_void);
}
```
（`AASSET_MODE_STREAMING = 2`）

### 5.4 cc-rs 在 NDK r27 上无法自动探测编译器

```
error occurred in cc-rs: failed to find tool "clang++.exe": program not found
```
cc-rs 1.4.6 找的是**无 API 版本号**的名字（`x86_64-linux-android-clang++`），
而 NDK 只提供带 API 号的（`x86_64-linux-android26-clang++.cmd`）。
`tauri android build` 会自己注入，**裸 `cargo` 不会**。

→ 已固化进项目根 `.cargo/config.toml` 的 `[env]`：`CC_/CXX_/AR_<triple>` +
`CARGO_TARGET_<TRIPLE>_LINKER`（后者尤其重要，否则默认 linker 是宿主 `cc`）。

### 5.5 Tauri 生成工程的默认值是 `minSdk = 24`

不是我们定的 26。正式工程要改，而且要和 NDK 包装器的 API 号（我们用 26）对齐。

### 5.6 Tauri resources 的 assets 前缀 = 无前缀

`"resources": { "resources/probe.bin": "probe.bin" }` → APK 内是 `assets/probe.bin`。

### 5.7 ✅ `libc++_shared.so` 的坑**不用我们填**

tauri-cli 在链接后会自己解析 `.so` 的依赖并 symlink 进 jniLibs：

```
Info lib "libm0_probe_lib.so" requires "libc++_shared.so"
Info symlinking sysroot/usr/lib/x86_64-linux-android/libc++_shared.so
     in jniLibs dir ".../jniLibs/x86_64"
```

所以 `docs/06` 风险 R1 里那条"`dlopen failed: libc++_shared.so not found`"
**在 Tauri 2 路径下不会发生**（只要 `Cargo.toml` 开了 `oboe-shared-stdcxx`）。
`.so` 的依赖清单里也能看到 `liblog.so` / `libandroid.so`（我们新增的两个 FFI 链接项）正常，
`libOpenSLES.so` 来自 Oboe。

### 5.8 ⚠️ debug APK 有 ~131 MB 的**孤儿条目**（发布包必须复查）

实测 debug APK **311.1 MB**，但中央目录里 928 个条目的压缩合计只有 **180.2 MB**。
直接解析 zip 结构发现：

| 项 | 值 |
| :--- | :--- |
| 中央目录条目数 | 928 |
| **本地文件头数量** | **3021** |
| 孤儿/重复条目 | **2093** |
| 浪费空间 | **≈ 131 MB**（正好等于 `libm0_probe_lib.so` 又存了一遍） |

即"写了又被重写、旧数据留在文件里"。debug 包无所谓，但**发布包必须查**，
否则最终 APK 可能凭空翻倍。

→ 已加 `scripts/audit-apk.sh`，用本地文件头 vs 中央目录的数量差来判定。

**后续验证（同一天）**：清掉 `jniLibs/x86_64/`（确认陈旧 ABI 目录已被移除、
日志里能看到 `✗ 清除陈旧 ABI 目录 x86_64/`）后重建，APK **仍是 307 MB** ——
说明这 ~132 MB 重复**不是陈旧 ABI 造成的**，而是
**arm64 的 `libm0_probe_lib.so`（137 MB，debug 未 strip）被写了两遍**。

→ 这是 **debug 构建 + 未 strip 的巨型 `.so` + `keepDebugSymbols`/对齐**共同导致的打包行为。
**必须在 release 构建上复验**：release 会 strip，`.so` 会小一个数量级；
如果那时仍有重复，才需要去调 AGP 的 packaging 配置。

### 5.9 环境坑（构建工具链层面）

| 坑 | 现象 | 处理 |
| :--- | :--- | :--- |

### 9.1 ⚠️ 真机新增的两条环境坑（都卡了时间）

**① `pm install /sdcard/...` 必失败** —— `/sdcard` 是 FUSE 存储，`system_server` 读不了：

```

  (from path /sdcard/Download/xxx.apk, context u:r:system_server:s0)

```
→ 正确姿势：`adb push <apk> /data/local/tmp/x.apk` 然后 `pm install`。
实测 `adb push` 有 **97 MB/s**，175 MB 的包 1.8 秒传完。

**② `adb install` 在 ColorOS 上会卡在手机侧确认流程**（实测 4 分钟不返回）。
根因是 ROM 把确认交给了默认安装器 App，而那个 App（本例是 InstallerX Revived）
读不到系统安装器的 FileProvider：

```
Permission Denial: opening provider androidx.core.content.FileProvider from
  ProcessRecord{... com.rosan.installer.x.revived ...}
  that is not exported from UID 10212
```
`adb shell pm list packages -U | grep 10212` → **UID 10212 = `com.android.packageinstaller`**。

> **这个报错与我们的 APK 完全无关**，是「第三方安装器 App ↔ ROM 系统安装器」之间的兼容问题。
> 绕开方式就是走 `/data/local/tmp` + `pm install`（不经过任何安装器 App）。
> 如果必须手动装，先在「设置 → 默认应用」里把安装器切回系统安装器，或用 Shizuku/root 模式的安装器。

**③ ~~ColorOS 上 logcat 拿不到应用侧日志~~ → 已更正：logcat 可用，是 buffer 被别的进程刷爆了。**

> ⚠️ **这条我先给出了错误结论，半天后实测推翻，记录下来避免再踩。**
>
> **当时的观察**：真机 55 秒窗口内 `grep -c PROBE` = **0**，连 `eprintln!` 的
> `RustStdoutStderr` 都没有；而同一个包在模拟器上日志一切正常。于是判为
> "ROM 层面没把应用侧日志吐给 adb"。
>
> **实测真因**（2026-09-18 13:04 那次长块扫描，日志完整拿到）：
> `adb logcat -d -s PROBE:V` **能正常返回我们的日志**：
> ```
> I/PROBE   (27730):    mel.time=  4096 | audio [1, 1, 2097152] = 47.55s 音频 | ...
> I/RustStdoutStderr(27730): [PROBE]    mel.time=  4096 | ...
> ```
> 而真凶是**这台机器上有个后台应用在疯狂刷日志**——每约 200 ms 一条：
> ```
> D/AndroidRuntime(30234): Calling main entry com/xingin/tiny/daemon/e
> D/AndroidRuntime(30475): Calling main entry com/xingin/tiny/daemon/e
> ```
> logcat 是**环形 buffer**，被这样刷几十秒后，早先的 PROBE 行就被挤出去了。
> 那次留下的只有**最后几行**（探针 0 / 1 / 4 / 3a 与 64–1024 档全被覆盖），
> 所以看起来像"完全没日志"。
>
> **验证命令**（看清 buffer 被谁占满）：
> ```bash
> adb -s <serial> logcat -d -v brief | awk '{print $1}' | sort | uniq -c | sort -rn | head
> ```
>
> 另一个**误导性中间结论**也别再走一遍：logcat 里能看到
> `D/CommonApp-205-10505(...)`，而 **10505 正是本 App 的 uid**，很容易以为
> "日志被包了一层壳 tag"。实测该 tag 下只有 **23 行 ROM 框架自己关于该 App 的记录**
> （`transport layer data is invalid` / `scene=COMMON pn=...`），**不是 App 的输出**。

**结论不变，但理由要换**：真机诊断仍应以**落盘**为首选通道 ——
不是因为"ROM 封锁"，而是因为 **logcat 是被动接收 + 有损的**（环形 buffer 会被任何
话痨进程覆盖、`-c` 一清就没了、时序不可控）。而落盘是**主动、无损、可归档**的。

`run-as` 对 debuggable 包有效，ColorOS 上实测可用：

```bash
adb exec-out run-as com.hifishifter.m0probe cat probe.log
```
一条命令拿全文，可 grep、可 diff、可归档 —— 不需要人肉翻页截图
（用 `input swipe` 滚动日志区时很容易滑到外层容器，实测被用户指出过）。

→ **设计结论：真机诊断必须有「落盘」这条通道。**
完整的可取回性排序是 **落盘(run-as) > logcat > 截图**。
`scripts/run-probe.sh` 已按这个优先级实现（落盘取不到才回退 logcat，最后才提示截图）。

**已把上面三条固化：**
- 安装环节改成 `push /data/local/tmp` + `pm install -r -t -d`，
  并自动 `settings put global verifier_verify_adb_installs 0`；
- 探针 `log()` 增加落盘通道（`app_data_dir/probe.log`，由 `setup` 里 `init_file_log` 初始化）；
- 收集环节按 `run-as` → `logcat` → 截图提示 的优先级兜底。

## 10. 探针 3b：真实模型（`pc_nsf_hifigan.onnx`）加载实测

在真机（arm64 / PKR110）上用 `adb push` 把上游的
`backend/src-tauri/resources/models/nsf_hifigan/pc_nsf_hifigan.onnx`（53 MB）
放到 `/data/local/tmp/`，探针自动发现并加载。

```
模型 = /data/local/tmp/pc_nsf_hifigan.onnx（53 MB）
✅ Session 就绪，耗时 105 ms
输入：
  · mel  (Float32, shape [-1, 128, -1], 符号 ["batch", "", "time"])
  · f0   (Float32, shape [-1, -1],     符号 ["batch", "time"])
输出：
  · audio (Float32, shape [-1, 1, -1], 符号 ["batch", "", "time"])
执行提供者 = 默认（CPU）
```

### 10.1 关键数字

| 项 | 值 | 意义 |
| :--- | :--- | :--- |
| **Session 创建（53 MB 模型）** | **105 / 125 ms**（两次运行） | 冷启动加载声码器的代价可忽略 |
| 模型输入规格 | `mel [-1,128,-1]` / `f0 [-1,-1]` | **上游改造直接可用**，不用再猜 |
| 模型输出规格 | `audio [-1,1,-1]` | 同上 |
| **单次推理（64 帧 mel）** | **321 ms** → 输出 `audio [1, 1, 32768]` | 见下方换算 |
| 内存（含 WebView） | 加载后 **390 MB** → 推理后 **400 MB** | **R3（OOM）的第一手基线** |

**推理性能换算（很关键的正面结论）**：
`mel` 的 `time` 填 64 帧 → 输出 32768 个采样点。
按 44.1 kHz 算就是 **0.743 秒的音频**，而推理只花 **321 ms** →
**RTF ≈ 0.43，比实时快约 2.3 倍**。

也就是说：**这台手机（PKR110）上声码器推理不是瓶颈**，
可以做"边播边合成"而不必预先全曲合成。内存增量也很温和（+10 MB）。
> ⚠️ 注意这只是 **64 帧（约 0.74 s）** 的短块。
> 上游实际会喂更长的块（`nsf_hifigan` 有长块优化分支
> `feat/hifigan-long-chunk-optimization`），长块下的延迟与内存需要再测。

> 动态维（`-1`）说明：`nsf_hifigan` 是**变长输入**，`time` 维由音频长度决定。
> 所以移植时不能按固定 shape 喂数据，必须按实际帧数构造 `mel` / `f0`，
> 并注意两个输入的 `time` 必须一致。

### 10.2 探针在此修掉的一个自身 bug（值得记）

第一版对动态维的处理是 `*d as usize` 再 `product()`。`-1 as usize` =
`0xFFFF_FFFF_FFFF_FFFF`，乘积直接溢出：

```
❌ 【ort_model】panic 已捕获（后续探针继续跑）：attempt to multiply with overflow
```

修法（两层）：
1. **先按有符号 `i64` 判断**动态维，再决定能不能转 `usize`；
2. 遇到动态维**填最小合法值**（batch=1，其余 64）而不是直接跳过 ——
   这样模型真能跑起来，能拿到**真实推理延迟与内存**，比只报"跳过"有用得多。
   注意 `mel` 与 `f0` 的 `time` 维要填成同一个值，否则 shape 不匹配。

> `catch_unwind` 兜底在这里又救了一次：panic 被捕获，后面探针 2（cpal 出声）
> 照常跑完（262860 样本 / 3 秒）。**这就是「每个探针独立兜底」的价值。**

### 10.3 复跑方式（不需要重新构建 APK）

探针故意不从 APK assets 里找模型（否则每次安装都要多传 54 MB），
而是去这几个位置找，`adb push` 即可换模型：

```bash

echo -n /data/local/tmp/别的模型.onnx > /tmp/p.txt

```

## 11. 探针 3b 扩展：推理长度扫描（RTF 曲线 + 内存基线）

### 11.1 为什么要扫多个长度

`nsf_hifigan` 的 `time` 维是动态的（`-1`），上游实际会喂不同长度的块。
**只测一个长度会给出误导性结论**——可能把 ORT 针对新 shape 的首次图优化开销
当成稳态开销。所以探针改成：同一 Session 连续跑 5 档，
每档**冷跑 1 次 + 热跑 3 次取中位**。

填充规则：`mel [-1,128,-1]` 与 `f0 [-1,-1]` 的第 0 维（batch）固定填 1，
其余动态维填当前档位长度（两者必须一致，否则 shape 不匹配）。

### 11.2 结果（真机 PKR110 / arm64 / 默认 CPU EP）

| `mel.time` | 输出 | 音频时长 | 冷跑 | 热跑 ×3 | 中位 | **RTF** | **RSS** |
| ---: | :--- | ---: | ---: | :--- | ---: | ---: | ---: |
| 64 | `audio [1,1,32768]` | 0.74 s | 295 ms | 344 / 356 / 358 | 356 ms | **0.479** | 389 MB |
| 256 | `audio [1,1,131072]` | 2.97 s | 1459 ms | 1447 / 1452 / 1453 | 1452 ms | **0.489** | 438 MB |
| 1024 | `audio [1,1,524288]` | 11.89 s | 5778 ms | 5746 / 5752 / 5753 | 5752 ms | **0.484** | 602 MB |
| 4096 | `audio [1,1,2097152]` | 47.55 s | 21964 ms | 21898 / 21936 / 23967 | 21936 ms | **0.461** | **1242 MB** |
| 16384 | — | — | 跳过 | — | — | — | 上一档超 8 s 预算，不再往更长测 |

### 11.3 结论一：RTF 恒定 ≈ 0.48 ⇒ 声码器不是瓶颈，可以边播边合成

四档 RTF 落在 0.461–0.489 的窄带内，**几乎不随块长变化** ⇒
开销主体是**线性卷积**（上采样层），没有非线性膨胀。

- **比实时快约 2.1 倍**：合成 1 秒音频只需约 0.48 秒。
- 余量 2 倍 ⇒ **可以做「合成线程 + 播放线程消费环形缓冲」的流式方案**，
  不必预先合成整曲。冷跑与热跑差值也很小（首档 295→356 ms），
  说明 ORT 的图优化对**同一 shape 只发生一次**，且成本不高。

> 对比第一版单点测量（只测 64 帧）得到的 RTF 0.43 —— 数量级一致，
> 但那时是**单次冷跑**，把优化前的数字当成了稳态。多档扫描才看出真实是 0.48。

### 11.4 结论二：内存与块长强相关 —— 这是 R3（OOM）的真正形态

RSS 从 389 MB 单调涨到 **1242 MB**。基线约 390 MB 是 WebView + Tauri 运行时，
所以**推理相关增量**是：

| `mel.time` | 音频时长 | 推理相关 RSS 增量 |
| ---: | ---: | ---: |
| 64 | 0.74 s | ≈ 0 |
| 256 | 2.97 s | ≈ 50 MB |
| 1024 | 11.89 s | ≈ 210 MB |
| 4096 | 47.55 s | **≈ 850 MB** |

**注意两点，避免误读**：

1. 这是**同一 Session 连续跑 5 个不同 shape** 的水位。ORT 的 BFC arena
   会保留分配过的最大块且不归还 OS，所以 1242 MB 反映的是"处理过 4096 帧之后"的
   水位，**不是单次 4096 帧的瞬时需求**。
2. 但**生产环境就是这个用法**——一个 Session 要处理任意长度的音频，
   所以这个数字比"每档新建 Session"更贴近真实。

**设计结论**：

- 块长 ≤ **1024 帧（≈12 秒音频）**时，RSS 约 600 MB，**安全**。
- 块长 4096 帧（≈47.5 秒）时 RSS 1.2 GB，**对中低端机是危险区**
  （Android 单进程内存上限视机型在 512 MB–2 GB 之间，且还要留 WebView 的份）。
- ⇒ **上游必须限制单次合成的块长**，或者对超长 clip 做分段合成。
  `docs/02` 里要把这一条列为具体实现约束，而不是笼统的"注意内存"。

### 11.5 复跑方法（不需要重新构建 APK）

模型走 `/data/local/tmp` 发现（见 §10.3），所以换模型/改块长只要重启 App：

```bash

adb shell am start -n com.hifishifter.m0probe/.MainActivity
```

每档有 8 秒冷跑预算（`COLD_BUDGET_MS`）保护，避免在用户手机上跑太久。

### 11.6 还没测的

- **长块优化分支的实际收益**：上游有 `feat/hifigan-long-chunk-optimization`
  （2026-05-12，基于旧架构），没测。
- **NNAPI / XNNPACK EP**：目前只测了默认 CPU EP。上 EP 可能显著改 RTF，
  但需要验证算子覆盖与精度（见 `docs/06` 风险 R2）。
- **多线程**：ORT 的 intra-op 线程数没有调过。手机大小核调度下
  线程数不一定越多越好，需要扫一遍。
