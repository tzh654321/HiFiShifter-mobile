# 03 · 触控交互适配方案

> 前提：**没有键盘、没有右键、没有中键、没有滚轮、没有 hover、没有修饰键（Ctrl/Alt/Shift）**；**有多指（1–10 点触控）**。
> 基线读数（`frontend/src/`）：`onContextMenu` 45 处、`e.button` 判断 61 处、`wheel` 相关 124 处、`keydown`/`onKeyDown` 115 处、`hover:` 116 处、`touchAction` 仅 2 处。

---

## 1. 核心设计原则

桌面版的交互其实是「**用修饰键和鼠标按键给同一个拖拽动作附加语义**」。触屏没有这些，因此只有两条路：

| 思路 | 说明 | 采用 |
| :--- | :--- | :--- |
| **A. 状态化替代瞬时修饰键** | 把"按住 Ctrl 拖 = 复制"改成"切换到复制模式再拖"；把"按住 Shift 关吸附"改成"吸附开关" | ✅ 主路径。可发现性最好，适合触屏 |
| **B. 多指手势替代鼠标键/滚轮** | 双指 = 平移，捏合 = 缩放，长按 = 右键 | ✅ 主路径。零 UI 成本 |
| C. 手势 + 计时（长按 400 ms 后行为改变） | 例如长按块体进入"内部偏移" | 🔶 辅助，仅用于低频操作 |

**必须在设计阶段就定下来的两条铁律**：
1. **单指永远只做"最直接的语义"**（点选、拖动、绘制）。所有"第二语义"交给双指、长按或模式切换。这样用户不会误触。
2. **每个桌面版的"修饰键组合"都要有一个可见的 UI 入口**（浮动工具条 / 模式按钮 / 设置项），不能只靠隐藏手势。

| # | 决策 | 选项 | 建议 |

## 4. 技术实现要点

### 4.1 好消息：上游已经用 Pointer Events

`pointerdown` 48 / `pointermove` 91 / `pointerup` 119（`onPointerDown` 105）——**没有用 `mousedown`/`touchstart` 的混杂写法**（`touchstart` 0 处，`mousedown` 仅 10 处）。这意味着触控迁移的基础是好的：Pointer Events 天生同时支持鼠标和触摸。

**真正要改的是**：
- 61 处 `e.button` 判断：触摸事件的 `button` 恒为 `0`，`e.button === 2` 的分支在触屏上**永远不会触发**。必须为这些分支补上替代入口。
- `e.buttons & 1`（`usePianoRollInteractions.ts:1890`）同理。
- 45 处 `onContextMenu`：Android WebView **长按会原生触发 `contextmenu` 事件**，所以这部分可能"免费"可用，但必须：
  - 加 `longpress` 的视觉反馈（否则用户不知道按多久）
  - 阻止系统的文本选择/上下文菜单（`-webkit-touch-callout: none`）

### 4.2 Android WebView 的滚轮合成（已实测待验证的复用机会）

Chromium/Android WebView 会把多点手势**合成为 `wheel` 事件**：
- **双指捏合 → `wheel` 且 `ctrlKey === true`**
- **双指拖动 → `wheel`（`deltaX`/`deltaY`）**

而 `frontend/src/components/layout/wheelGesture.ts` **已经实现了触摸板轴向识别**（`isLikelyTouchpadWheelGesture`、`getParamEditorWheelAction`、`getTimelineWheelAction`，含 `free-scroll` / `horizontal-zoom` / `vertical-zoom` 等语义）。而且合成 wheel **在手指中点位置派发**，现有的"以指针为锚点缩放"路径取的就是事件坐标——**所以理论上"缩放中心为两指中点"可能已经免费成立**。

> ⚠️ **但最终决策是：Android 上以自己实现的手势层为主，不用 wheel 合成路径。**
> 原因是你的需求是**两轴独立缩放与平移**，而 wheel 合成路径的语义是"`Ctrl`+wheel = 水平缩放"，**拿不到竖直轴的独立控制**，也拿不到"中点平移"的语义。
> 两条路**绝不能同时生效**（会双重缩放）。手势进行中必须屏蔽合成 wheel。完整的取舍分析与 M0 实测清单见 [08 文档 §6](08-双指手势与视口内核对接规范.md)。

### 4.3 必须新增的样式与全局处理

```css
/* 作用于所有可交互画布/时间线/参数区 */
.touch-surface {
    touch-action: none;           /* 自己处理手势，禁止浏览器滚动/缩放 */
    -webkit-user-select: none;
    -webkit-touch-callout: none;  /* 禁止长按弹出系统菜单/选择 */
    overscroll-behavior: contain; /* 禁止下拉刷新与滚动链 */
}
```

```html
<!-- index.html viewport 需改 -->
<meta name="viewport"
      content="width=device-width, initial-scale=1.0,
               maximum-scale=1.0, user-scalable=no,
               viewport-fit=cover">
```
- `user-scalable=no`：防止误触双指缩放整个页面（这是桌面版没有的问题；桌面版 viewport 目前无此限制也不影响）
- `viewport-fit=cover`：配合安全区 CSS（见 04 文档）

其他必须处理的 WebView 默认行为：
- 长按选词/放大镜 → `user-select: none`
- 图片拖拽 → `draggable="false"`
- 双击缩放 → `touch-action: manipulation` 或 `none`
- 文本输入弹出的软键盘顶起布局 → 用 `visualViewport` API 或 Android `adjustResize`

### 4.4 多指手势层的实现方案

新增一个独立模块，**不侵入现有交互代码**：

```
frontend/src/touch/                 ← 新增
├── useTwoFingerViewport.ts         ← 双指两轴缩放/平移 → 内核原子写入（规范见 08 文档）
├── gestureRouter.ts                ← 手势 → 动作路由（可注册/可禁用）
├── longPress.ts                    ← 长按识别（400ms / 位移容差 10px）
├── haptics.ts                      ← 触觉反馈封装
├── touchMode.ts                    ← 工具模式状态（指针/画笔/橡皮/伸缩/偏移）
└── layoutMode.ts                   ← phone / tablet / desktop 判定（见 07 文档 §2.3）
```

设计要点：
- **视口类手势不要自己维护状态**：双指两轴缩放与平移全部落到 `renderKernel/scrollKernel` 的既有原子入口（`setViewport` / `setRowHeightAndScrollTop`）。**完整规范、数学公式、轴向保护、状态机、提交时序见 [08 文档](08-双指手势与视口内核对接规范.md)**——那份文档是本节 §4.4 的实现依据。
- **手势层只发语义事件**（`gesture:two-finger`、`long-press`），由各面板订阅。这样面板代码的改动最小。
- **每个 pointerId 独立跟踪**，用 `Map<number, PointerState>`；不要用单个 ref 存"当前指针"。
- **进入双指时必须立刻干净地终止单指正在进行的操作**（例如正在绘制曲线时第二指落下）。上游 `App.tsx:3423` 附近已有"窗口失焦时按 pointerup 收尾拖拽"的实现（提交 `2472acb0`），**照抄那个收尾路径**即可，不要另写一套。
- **手指数变化时的状态机**要严格：0→1（PENDING，位移 >8px 或 200ms 后才 ACTIVE）→2（取消单指操作，转入手势）→1（进入 **150 ms 冷却期**，忽略单指操作，避免抬手残留误触）→0。
- **手势进行中要屏蔽**：合成 wheel、长按识别器、双击检测——否则会出现"捏合过程中弹出上下文菜单"。

### 4.5 触觉反馈（很重要）

Android 用户对"操作有没有生效"的判断高度依赖振动。建议在这些时机给反馈：
- 长按达到阈值（进入上下文菜单前）
- 吸附（snap）到网格/播放头时
- 拖拽到无效区域被拒绝时
- 跨越时间线/参数面板边界时

实现：`navigator.vibrate()`（WebView 支持，需 `VIBRATE` 权限）或 Tauri 的 haptics 插件。

## 7. 每表面轴向策略 + 拍数栏触摸 seek（2026-09-21）

用户报的两条「缩放没反应」，根因都不在公式上，而在**事件够不够得着**：

| 现象 | 根因 |
| :--- | :--- |
| 轨道界面：拍数栏横向缩放无效、轨道列纵向缩放无效 | 这两块**从来没被注册成手势表面**。时间线只 `attachSurface(getContainer())` 挂了一个滚动容器，拍数栏与轨道列在它的 React 树之外（拍数栏是滚动容器上方的兄弟行），双指事件根本不进状态机 |
| 参数界面：拍数栏 / 琴键列上捏合会**顺带改另一轴** | 两块都注册了，但**没限制轴向**：琴键列上竖向捏合顺带改 pxPerSec，横向捏合顺带改 rowHeight（本节 7.1 修的就是这条）|
| 参数界面：钢琴栏纵向缩放「像没生效」 | **不是轴向问题**（实测 `vZoom:true`、`ky≠1` 都成立）—— 是值域 ref 不回写，导致下一次手势的基准陈旧、缩放被拽回。见 §7.5 |
| 参数界面：拍数栏点击不移动播放红线 | 它的 seek 只有鼠标路径（标尺 `onMouseDown` + `isLegacyMouseEventFromStylus()` 守卫），触摸不走 §7.3 那条 pointer 路径 —— 该路径本次只加到了**时间线**，参数面板尚未同样接线（待办）|

### 7.1 轴向策略：`attachSurface(el, axis)`

`TwoFingerGestureController` 新增：

```
attachSurface(el, axis: "both" | "x" | "y" = "both")
```

会话开始时由 `axisForSession()` 定轴向，判据是**两指各自落在哪个表面**（`pointerSurface` 在 pointerdown 时已记好）：

- 都在同一个带轴向的表面 → 用该表面的轴向；
- 只有一个落在受限表面（跨区：一拍数栏 + 一画布）→ 用那个受限轴向（这才是跨区手势的常见意图）；
- 两个受限表面轴向不同（拍数栏 x + 轨道列 y）→ 退回 `both`（限制任一轴都会与另一侧的期望冲突）；
- 都没落在受限表面（都在画布上）→ `both`，与改造前完全一致。

`update()` 里被禁的那一轴**既不缩放也不平移，且完全不调用 viewport 提交** —— 少一次写入就少一次 React 提交。

### 7.2 ⚠️ 挂表面必须一起决定 `touch-action`

主容器靠 `attach()` 里的 `touch-action: none` 拿事件。**额外表面没有这层**，所以：

| 表面 | 处理 | 为什么 |
| :--- | :--- | :--- |
| 拍数栏 | `touch-action: none`（直接禁） | 它自己不滚动（内容由内核 transform 驱动），禁掉最省事 |
| 轨道列 | **不能**禁 —— 换成 `suppressTwoFingerScroll(el)` | 它是**原生竖向滚动容器**；禁掉会把「单指滚轨道」这个基础操作弄没（回归，用户没要求） |

`touch-action: pan-y` 也不行：它声明"竖向平移交给浏览器"，于是双指竖向捏合被当成滚动 ⇒ 浏览器发 `pointercancel`，捏合收不到。
可行做法是在 `touchstart`/`touchmove` 里**只在 `touches.length >= 2` 时** `preventDefault()`：按规范这能在滚动开始前取消默认行为（单指时不动），而 `pointerdown` 在该 `touchstart` **之前**已派发 ⇒ 控制器的双指状态机不受影响。已封装成 `suppressTwoFingerScroll(el)`（`touchGesture.ts` 导出）。

### 7.3 拍数栏「点一下就移动播放红线」

时间线标尺的 seek 走 `TimeRuler` 的 `onMouseDown`，而它第一行是：

```ts
if (isLegacyMouseEventFromStylus()) return;
```

`isLegacyMouseEventFromStylus()` 判的是"上一个真实指针是不是 pen 或 touch" —— **对 touch 也返回 true**。所以手机上点/拖拍数栏**完全没反应**。

补一条**指针事件**路径（`bindRulerTouchSeek`）：

- 鼠标不接管（仍走原路径，桌面语义不变）；
- `e.isPrimary` + 单指在案 + 无手势会话才接管；按下即 `commit` 一次，拖动期间 `commit=false` 预览，抬手再 `commit` 一次；
- 第二指落下（双指会话起来）立刻让位，不抢事件；
- 落点函数经 `rulerSeekRef` 由 `setPlayheadFromClientX` 填充（effect 顺序保证在手势 effect 的 rAF 重试之前写好）。

### 7.5 🔴 参数编辑器「纵向缩放像没生效」的真根因：值域 ref 不回写

用户口径：「参数界面……钢琴栏要只能纵向（**目前钢琴栏的纵向缩放根本就没缩放**，只是少显示了几个琴键）」。

实测把两件事分开了：

| 观测 | 值 |
| :--- | :--- |
| 会话内部量（新增 `window.__hsGestureDebug`）| `axis:"both"`、`lockY:false`、`multi:false`、`armed:true`、**`ky:2.2749`**、**`vZoom:true`**、`rowH0:18.417` |
| 由 `ky` 反算目标行高 | `18.417 × 2.2749 = 41.9` ⇒ `span = 442/41.9 = 10.55`（**变了**）|
| `__hsParamViewport().span` | **不变** |

⇒ 捏合的**缩放确实算出来了**、也提交给了内核（`syncVerticalScrollbarForViewport` 就地刷新了
`kernelDataRef.valueDomain.span`），**但 `pitchViewRef` 没被写**。

`setPitchView(next)` 会 `pitchViewRef.current = next` 再调 `syncVerticalScrollbarForViewport`；
而**双指手势的 `setVertical` 直接调后者**，绕过了 `setPitchView` ⇒ ref 永久落后于内核。

后果不只是"读数是旧的"：
- `viewport.get()` → `valueToRow()` 从**这个 ref** 反算 `rowHeight` / `scrollTop`；
- 于是**下一次**手势的基准 `rowHeight0` / `scrollTop0` 是陈旧的 ⇒ 一松手再捏就**跳回去**，
  用户读作"根本没缩放，只是少显示了几个琴键"（缩放瞬间确实生效，但立刻被下一次手势拽回）。

**修法**：`syncVerticalScrollbarForViewport` 里回写 ref，让 ref 与内核镜像同步：

```ts
if (param === "pitch") pitchViewRef.current = clampedView;
else paramViewsRef.current[param] = clampedView;
```

顺带把内核 → React 的写回路径（`pitchViewRef.current = { center, span: current.span }`）也修正了 ——
它原先保留的 `current.span` 正是那个陈旧值。

### 7.6 调试钩子 `window.__hsGestureDebug`

`update()` 每帧写一个只含基本类型的对象，暴露「这一轴为什么没动」：

```
{ axis, allowX, allowY, lockX, lockY, multi, armed, kx, ky, vZoom, rowH0, rowH }
```

判读规则：

- `lockX/lockY` = 会话起手时该轴两指间距 < 24px ⇒ 该轴**不缩放**（但可平移）；
- `multi` = 指针数 ≥ 3 ⇒ 退化为纯平移（三指语义）；
- `armed:false` = 位移还没超过死区 16px ⇒ 整个会话都还没开始生效；
- `vZoom:false` = 该内核明确不做纵向缩放（行高恒定，捏合退化为纯平移）。

🕳️ **`rowH` 字段读的是 `viewport.get()`**，对参数编辑器而言那条路会经过值域 ref ——
ref 陈旧时它会**撒谎**（显示与 `rowH0` 相同的旧值）。要判"内核真值有没有变"，看 `ky × rowH0`
反算，或看 `__hsViewport()`（时间线的 `get()` 直接读内核，没有这层 ref）。


### 7.7 水平捏合锚点漂移 3.66px 已定位到**内核内容原点偏移**（数学已闭合）

上一轮留下「drift ≈ 3.9px 的固定锚点偏移，未定位」。本轮把公式推完了：

控制器提交的是 `newScrollLeft = secAtMid0 · P₁ − mid.x`，其中 `secAtMid0 = (S₀ + mid₀.x)/P₀`。
若**内核的 screen↔sec 映射存在常数偏移 C**（内容原点不在容器左边缘），即真实秒数为
`(mid.x + scrollLeft − C)/pxPerSec`，那么锚点在缩放前后的真实漂移为：

```
Δsec = C·(1/P₀ − 1/P₁)        漂移(px) = Δsec · P₁ = C · (P₁/P₀ − 1) = C · (k − 1)
```

实测 `k = 1.935`、漂移 `3.66px` ⇒ **C ≈ 3.9px**。数学关系完全吻合，且能解释
「两平台逐位一致」（C 是布局常数，与设备无关）与「平移不漂移」（平移只用到 Δmid，
C 被消掉 —— 实测双指平移 Δ = −60.000 精确）。

**旁证**：容器与内核滚动元素的 `getBoundingClientRect().left` **都是 132**（DOM 侧无偏移），
且 DOM 里所有元素的 `scrollLeft` 都是 0 —— 内核是**虚拟滚动**（canvas 渲染），
所以 C 只可能来自内核自己的坐标映射，不在 DOM 布局里。

**为什么本轮不修**：`C·(k−1)` 在 1.935× 缩放下是 3.66px ≈ 0.9ms，**肉眼不可见**；
而修它要动内核的 screen↔sec 映射（`applyViewport` / `ScrollKernel`），
属于高风险低收益。**遗留项**：若要修，正确做法是让 `viewport.get()` 暴露该偏移
（例如 `contentOriginX`），控制器公式改为 `(S + mid.x − C)/P` 与 `… − mid.x + C`。

### 7.8 验收工具的两个坑（本轮新踩）

| 坑 | 现象 | 对策 |
| :--- | :--- | :--- |
| **CDP 求值的函数不是闭包** | 探针里写了 `function collectTimes(){…}`，在另一个函数里调用 → `xxx is not defined` | CDP 只序列化**这一个函数**的源码；每个函数必须**自包含** |
| **轴向上限会伪装成"没生效"** | 轨道列纵捏报「无变化」，其实 `rowHeight` 已经是上限 192 | 验收前先确认目标轴有余量；探针加 `--dir in`（向内捏 = 缩小）再测一次 |

同理，**观测量必须选对**：拍数栏上的 `0:0.000` 是**小节刻度标签**（与播放头无关、点前后恒定），
拿它判 seek 必然误判成"未生效"；正确的是**播放头红线元素自身的 `getBoundingClientRect().left`**
（见 `scripts/_probe-tapseek.mjs`）。
