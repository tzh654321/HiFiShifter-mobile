# 13 · 验收工具链（CDP）与手势层的前置修复

> 目的：把 `docs/05` §8.5 定的验收方式（**模拟点击/划动/多指，逐项验「看得到 + 点得到」**）
> 变成可复跑的工具，并用它跑出**布局改造前的基线**。
> 相关：`docs/05` §8.5（验收标准）、`docs/12`（真机验证）、`docs/08`（双指手势与视口内核）

## 1. 为什么是 CDP

`adb shell input` **做不了多指**，而验收要求模拟双指。唯一可行通道是 WebView 的 devtools 协议。

好消息：**不用改任何代码就能用**。wry 在 debug 构建下会调
`WebView.setWebContentsDebuggingEnabled(true)`
（`wry/src/android/main_pipe.rs`，`#[cfg(any(debug_assertions, feature = "devtools"))]`），
所以 debug 包天然可调试。

实测（`hs-phone-tall` / Android 15 / WebView Chrome 124）：

```bash
PID=$(adb -s emulator-5554 shell pidof com.arounder.hifishifter | tr -d '\r')
adb -s emulator-5554 shell cat /proc/net/unix | grep devtools
#   @webview_devtools_remote_<PID>
adb -s emulator-5554 forward tcp:9222 localabstract:webview_devtools_remote_$PID
curl -s http://127.0.0.1:9222/json/list
```

`/json/list` 里除了页面信息，还顺带给了一条**独立佐证**：

```json
{ "screenY": 136, "height": 2192, "width": 1080, "visible": true }
```

`2400 − 136(状态栏) − 72(导航栏) = 2192` —— 与 `docs/12` §8 用像素量测得出的
inset 结论完全一致（虚拟机上独立复现）。

## 2. 工具

| 脚本 | 作用 |
| :--- | :--- |
| `scripts/lib/cdp.mjs` | 零依赖 CDP 客户端（Node 22 自带 `fetch` + 全局 `WebSocket`，不需要 `ws`/`puppeteer`） |
| `scripts/layout-audit.mjs` | 量每个可交互元素的矩形，判四类问题 + 两类提示 |
| `scripts/touch-drive.mjs` | `probe` / `find` / `eval` / `tap` / `swipe` / `pinch` / `pan2` |
| `scripts/_probe-shell-ui.mjs` | 移动端外壳：控件是否"看得到 + 点得到"（顶栏 / 工具行 / 底栏 / 页签 / 浮层溢出） |
| `scripts/_probe-appearance.mjs` | **外观设置面板**（2026-09-22）：①打开 ②排版全屏 ③Tab 切换 ④实时预览 ⑤关闭回滚 ⑥应用落盘，附面板内触摸目标分组统计。`--keep-open` 可保留面板给 `layout-audit` 接着审计 |
| `scripts/_probe-symlink.mjs` | 本机能否创建符号链接（`<src> <dst>`，换机器必跑；见 `docs/05` 附录） |
| `scripts/swap-so-in-apk.py` | **换掉 APK 里的某个 `.so`**：`<源apk> <目标apk> <条目名> <新so>`。arm64 的 gradle 打包失败时的绕行手段（`docs/15` §3），之后配 `zipalign -p 4` + `apksigner` |
| `scripts/_restore-from-bin.py` | **从回收站捞回文件**（按原路径关键字，只读不改桶）：`python scripts/_restore-from-bin.py "foo.apk" D:/out [--index 1]`。本机 `rm` 一律进桶且不释放空间，所以"删掉的"通常还在盘上 ⇒ 比重建快 |

```bash
node scripts/layout-audit.mjs --json report.json --top 8
node scripts/touch-drive.mjs find 帮助              # 按文字定位控件（输出中心点）
node scripts/touch-drive.mjs probe 235 16           # 该点命中谁、最近处理器宿主是谁
node scripts/touch-drive.mjs tap   235 16           # 真的点下去 + 前后状态摘要
node scripts/touch-drive.mjs pinch 180 500 40 140 600   # 双指缩放（两指沿水平撑开）
node scripts/touch-drive.mjs pan2  180 500 80 0 600     # 双指平移
node scripts/touch-drive.mjs eval  "window.visualViewport.scale"
```

### 两个必须知道的坑（都踩过）

1. **坐标系**：CDP 触摸坐标是 **CSS px、相对 WebView 视口**，与 `layout-audit.mjs` 的
   `rect` 同一套；**不是**截图的设备像素（差 `devicePixelRatio` 倍）。
   拿 1080 宽的截图坐标直接喂进 360 宽的视口，全都落在视口外。两个脚本都会对超范围坐标报警。
2. **React 的 `div onClick`**：不能只按 `tagName/role/tabindex` 判「可交互」——
   实测菜单栏那一行就是 `<div>`，会被误判成「点不到」。处理器藏在 React 挂在 DOM 节点上的
   `__reactProps$…` 里，要顺着冒泡链找**最近的处理器宿主**。

### 已知边界

**画布（canvas/WebGL）里的交互对象量不出来。** 时间线、钢琴卷帘都是画布渲染，
DOM 里只有一个 `<canvas>`。那部分的「看得到 + 点得到」只能靠 `touch-drive.mjs`
派发触摸后**观察状态变化**（状态摘要 / 截图比对），不能靠 `layout-audit.mjs`。

## 3. 基线（布局改造前，`hs-phone-tall` 360×731 CSS）

```
视口: 360×731 CSS px  (dpr 3)          ← 731 = (2400 − 136 − 72) / 3，即 docs/12 §8.5 的可用高度
可交互元素（可见）: 55

  offscreen        27   超出视口，看不到
  clipped          29   被不滚动的祖先裁掉，永远看不到
  occluded          6   中心点被别的元素挡住
  tooSmall         53   触摸目标 < 44 px
  needScroll        0
  needsTapArea      0

结论：🔴 56 个元素看不到
```

最严重的一条：工具栏那一行按钮 x 一直排到 **1028**（视口只有 360 宽），
越界 **692 px**，且被祖先 `div.rt-Flex.rt-r-ai-center` 裁掉 —— 即**不可滚动**，永远看不到。

这正是 `docs/04` 预判的「桌面布局塞进 360 px」，现在是可复跑的数字。
改造后重跑同一命令即可对照。

完整原始数据：`.setup/layout-audit-baseline.json`。

用 `touch-drive.mjs` 的**视觉佐证**：

```bash
node scripts/touch-drive.mjs find 帮助        # → span「帮助」 中心 (235.1, 15.5)  可点 ✅
node scripts/touch-drive.mjs tap  235 16      # → 状态摘要 bodyLen 258 → 289（菜单弹出）
```

截图见 `docs/screenshots/模拟器-点击帮助菜单.png`。注意那张图**同时**证明了两件事：
菜单确实被点开了（「看得到 + 点得到」），以及系统栏与应用各占其位（inset 修复在虚拟机上同样生效）。

## 4. 🔴 顺手发现的真问题：浏览器 pinch-zoom **抢走了双指手势**

### 现象

在时间线画布上做双指捏合，整个界面被放大了 —— 而且是**浏览器自己的页面缩放**，
不是应用的行为：

```
window.visualViewport.scale:  1  →  5
```

**含义**：双指事件根本没有落到应用手里，被 WebView 的 pinch-zoom 消费掉了。
也就是说，在把浏览器的缩放关掉之前，**自研手势层（④）一行都收不到事件**。

### 为什么默认是开的

- wry 只设了 JS/storage/media 类 `WebSettings`，**没有关缩放**
  （`wry/src/android/kotlin/RustWebView.kt` 里只有 `javaScriptEnabled` / `domStorageEnabled`
  / `setGeolocationEnabled` / `databaseEnabled` / `mediaPlaybackRequiresUserGesture`
  / `javaScriptCanOpenWindowsAutomatically`）。
- 前端 `index.html` 的 viewport 是 `width=device-width, initial-scale=1.0`，
  **没有 `user-scalable=no`**。

### 实测三种做法的对照（重启应用重置 scale=1 后各测一次）

| 做法 | 捏合前 scale | 捏合后 scale | 结论 |
| :--- | ---: | ---: | :--- |
| 什么都不做（基线） | 1 | **5** | 🔴 浏览器吃掉手势 |
| `user-scalable=no`（改 viewport meta，**不重载**） | 1 | 1 | 假象 |
| `user-scalable=no` + 重载 | 1 | **5** | 🔴 **被 Blink 忽略** |
| **`touch-action: pan-x pan-y`**（html/body/#root） | 1 | **1** | ✅ **有效** |

**`user-scalable=no` 不可靠**：Chrome/Blink 在 Android 上出于可访问性会忽略它 ——
不重载时的「有效」只是还没重新解析 viewport 的假象，重载后照旧放大到 5 倍。
**这类"文档上写着能行"的开关必须实测。**

不用 `touch-action: none` 而用 `pan-x pan-y`：只砍缩放，**保留内层 `overflow: auto`
面板的原生滚动**。桌面端无副作用（那里不存在 pinch-zoom）。

### 落地

`android/patches/0005-frontend-touch-action.patch`（1 文件 / 16 行，只动
`frontend/src/index.css` 的 `html, body, #root` 规则）。

> 为什么走前端补丁而不是原生侧 `WebSettings.setSupportZoom(false)`：
> 后者在 API 33+ 已废弃（且可能直接是 no-op，见 `docs/06` 的原则——
> **不靠推测，靠实测**）；而 `touch-action` 已经在真机同款 WebView 内核上实测通过。
