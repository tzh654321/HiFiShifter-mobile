# 08 · 双指手势与视口内核对接规范

> 需求原文：**「双指操作可以支持纵向与横向的缩放与平移，且缩放中心为两指中点。」**
> 本文把这个需求落到 `renderKernel` 的既有 API 上，并给出可直接实现的公式与状态机。

---

## 1. 结论先说：不要自己写视口数学，内核已经具备所需入口

核实 `develop` 的 `frontend/src/components/layout/renderKernel/scrollKernel.ts`（该文件是**视口真值的唯一事实源**），发现需要的四个动作**全部已有原子入口**，而且有一个方法是**专门为解决"纵向缩放时指针下内容漂移"而写的**：

| 需求动作 | 已有 API | 备注 |
| :--- | :--- | :--- |
| 水平平移 | `setScrollLeft(px)` | 内部钳制到 `[0, maxScrollLeft()]` |
| 竖直平移 | `setScrollTop(px)` | 内部钳制到 `[0, maxScrollTop()]` |
| **水平缩放（带锚点）** | `setZoom(pxPerSec, anchorScreenX): number` | 锚点语义 = "锚点下的工程时间不变"；**`anchorScreenX` 允许落在视口之外**（注释明确说明是为了避免"锚点被钉在视口边缘造成缩放漂移"）；返回值是**实际生效**的 pxPerSec，必须用来同步 React 派生量 |
| **水平「缩放 + 位置」原子提交** | `setViewport({pxPerSec?, scrollLeft?})` | 注释写明存在的原因就是"避免先用旧上限钳制新缩放"的中间态 |
| **竖直「缩放 + 位置」原子提交** | `setRowHeightAndScrollTop(px, scrollTop)` | 注释里给了实测根因：分两次写会出现 `2.975 → 3.273 → 2.975 → 3.279` 的**逐步振荡**，用户看到的是"缩放时纵向滚了一下" |

**因此本需求的实现性质是「把手势接到已有 API 上」，不是「新建一套视口模型」。** 这是本次移植里最大的一个去风险项。

### 1.1 还有两个免费得到的性质

**① 缩放中心为两指中点 —— 内核设计本来就支持**
`setZoom` 的 `anchorScreenX` **不夹取**到屏幕范围内（它有专门的注释解释为什么不能夹取）。两指中点是视口内的任意位置，甚至手指移出视口时中点会越界，内核都能正确处理。**这一条不需要我们做任何额外工作。**

**② 时间线上捏合，参数面板会自动跟随水平缩放**
时间轴内核每绘制帧通过 `onScrollLeftFrame` 把 `{scrollLeft, pxPerSec}` **整对**交给参数面板（`timeline/runtime/sharedViewportNotify.ts` 的 `shouldNotifySharedViewport`）。契约原文：

> 任一分量变化 → 通知（`scrollLeft` 与 `pxPerSec` 必须同帧一起送达，**不能拆成两次**）

也就是说，只要我们在水平方向上走 `setViewport` 的原子入口，**参数面板的水平缩放与位置联同是免费的**。反过来这也意味着：**水平方向绝不能写成"先 setScrollLeft 再 setZoom"两次调用**——那正好会破坏这个契约（该文件记录的缺陷就是这个原因导致的）。

### 1.2 明确不共享的部分

参数面板**只共享水平**（`pianoRollViewportBus` 的快照字段只有 `scrollLeft / pxPerSec / viewportWidth`，注释写明"参数编辑器不涉及竖直滚动与行高"）。所以：

- 时间线上双指纵向缩放 → **只影响时间轨道高度**，不影响参数面板
- 参数面板的"参数轴纵向缩放"是**另一套比例**（不是 `rowHeight`），需要单独处理 → 见 §7

## 2. 统一的「中点锚定」公式

不要分四种情况（纯平移/纯水平缩放/纯竖直缩放/复合）写四段代码。用**同一个公式**，平移会自动从缩放公式里退出来。

### 2.1 手势开始时的快照

```ts
interface TwoFingerSession {
    mid0: { x: number; y: number };       // 起始中点（宿主视口内 CSS px）
    span0: { x: number; y: number };      // 起始两指沿 X / Y 轴的分离度
    scrollLeft0: number;                  // 起始视口真值
    scrollTop0: number;
    pxPerSec0: number;
    rowHeight0: number;
    axisLock: { x: boolean; y: boolean }; // 该轴是否锁定（不缩放）
    zoomArmed: boolean;                   // 是否已越过缩放死区
}
```

### 2.2 水平轴

内容坐标用**秒**做锚（与 `setZoom` 的锚点语义一致）：

```
secAtMid0      = (scrollLeft0 + mid0.x) / pxPerSec0
targetPxPerSec = clamp(pxPerSec0 * kx, minPxPerSec, maxPxPerSec)     // kx = span.x / span0.x
newScrollLeft  = secAtMid0 * targetPxPerSec - mid.x
```

- **纯平移**（`kx = 1`）时自动退化为：`newScrollLeft = scrollLeft0 - (mid.x - mid0.x)` ✅
- **纯缩放**（中点不动）时自动退化为锚点缩放 ✅

提交：

```ts
const vp = kernel.setViewport({ pxPerSec: targetPxPerSec, scrollLeft: newScrollLeft });
// ⚠️ 必须用返回的 vp.pxPerSec 去同步 React 派生量（标尺刻度 / 内容宽度）
```

**要点**：`targetPxPerSec` 必须**先自己 clamp 再代入公式算 `newScrollLeft`**。否则当 pxPerSec 被上下限截断时，`newScrollLeft` 是用未截断值算的，提交后锚点会漂。

### 2.3 竖直轴

内容坐标用**行号**做锚：

```
rowAtMid0      = (scrollTop0 + mid0.y) / rowHeight0
targetRowH     = clamp(rowHeight0 * ky, MIN_ROW_H, MAX_ROW_H)        // ky = span.y / span0.y
newScrollTop   = rowAtMid0 * targetRowH - mid.y
```

提交：

```ts
kernel.setRowHeightAndScrollTop(targetRowH, newScrollTop);
// 一次调用、一次 commit、只通知一次订阅者 —— 不要拆成两次
```

**待确认（需实测）**：`setRowHeight` 的注释只说"非有限值或与当前值几乎相同时不做变更"，**没有提到上下限钳制**。所以 `MIN_ROW_H` / `MAX_ROW_H` 需要我们自己定义（建议 `28 ~ 240` CSS px），并且要和 `TrackList` 里已有的行高拖拽手柄用**同一组常量**，否则两条入口会互相打架。

### 2.4 两轴独立，互不干扰

`kx` 与 `ky` 分别由两指在 X / Y 轴上的分离度变化决定，所以：

| 手指动作 | kx | ky | 中点位 | 效果 |
| :--- | :--- | :--- | :--- | :--- |
| 两指同向上下移 | 1 | 1 | 移动 | **竖直平移** |
| 两指同向左右移 | 1 | 1 | 移动 | **水平平移** |
| 两指左右张合 | ≠1 | 1 | 基本不动 | **仅水平缩放** |
| 两指上下张合 | 1 | ≠1 | 基本不动 | **仅竖直缩放** |
| 两指斜向张合且移动 | ≠1 | ≠1 | 移动 | **两轴同时平移 + 缩放** |

这正好覆盖你要求的"纵向与横向的缩放与平移"。

## 3. 轴向保护（否则会误缩放）

两指手势最常见的问题是"用户只想滚动，结果缩放了一下"。三件事必须做：

### 3.1 缩放死区（先平移，后缩放）

手势开始后，**在分离度累计变化 < 16 CSS px 之前，强制 `kx = ky = 1`**，只做平移。
超过阈值后把 `zoomArmed = true`，并把**当时的中点与分离度重新取为基准**（`mid0` / `span0` 重置），这样越过死区的瞬间不会跳变。

### 3.2 单轴锁定（防止除零与爆炸）

若起始分离度 `span0.x < 24 px`（两指几乎竖着叠在一起），则 **`axisLock.x = true`**，整场手势 `kx` 恒为 1。
`span0.y < 24 px` 同理锁定 Y 轴。

这不只是为了数值安全（`span0` 趋近 0 时 `k` 会爆炸），更是交互正确性：手指捏得越"竖"，用户越想调竖直方向，不该让水平方向跟着抖。

### 3.3 三指 = 纯平移（可选但推荐）

三指拖动强制 `kx = ky = 1`。给用户一个"我绝对不想缩放"的干净通道。FL Studio Mobile 等 DAW 类 App 普遍提供这类"安全滚动"手势。

## 4. 手势状态机（防止脏状态）

手指数变化时的状态迁移是这类改动最容易出 bug 的地方。

```
        0 ──press──▶ 1(PENDING)
                       │ 位移 > 8px 或 超时 200ms
                       ▼
                    1(ACTIVE)  ← 单指操作：点选 / 拖动块 / 绘制曲线 / 框选
                       │ 第二指落下
                       ▼
                    cancelCurrentSingleOp()   ← 关键：必须处理，见 §4.1
                       │
                       ▼
                    2(PAN_ZOOM)  ← 本规范的主题
                       │ 第三指落下
                       ▼
                    3(SCROLL_ONLY)  ← kx = ky = 1
                       │ 手指减少到 2
                       ▼
                    2(PAN_ZOOM)（沿用现有会话，不重建）
                       │ 手指减少到 1
                       ▼
                    1(COOLDOWN, 150ms)  ← 关键：见 §4.2
                       │ 冷却结束
                       ▼
                    1(PENDING) → 0
```

### 4.1 `1 → 2`：必须干净地中止单指操作

用户正在参数面板画曲线时第二指点下来，此时必须：
- **按操作类型决定是"提交"还是"回滚"**：拖动音频块 → 提交到当前位置（符合直觉）；绘制曲线笔画 → 提交当前笔画；
- **释放所有 `setPointerCapture`**；
- **清空该面板的拖拽临时态**（`strokeRef` / `dragRef` / 预览层）。

上游在 `App.tsx` 里已有"窗口失焦时按 pointerup 处理拖拽"的先例（提交 `2472acb0 fix(timeline): window blur commits a drag like pointerup`），**可以照抄那个收尾路径**——这是现成的、已被验证过的"异常中止"处理方式。

### 4.2 `2 → 1`：必须冷却

只剩一指时，如果立刻转为单指操作，会出现经典的"抬手残留误触"：用户松开一根手指的瞬间，另一根手指的位置被当成一次点击/拖动起点，误改数据。

**必须插入 150 ms 冷却期**，期间忽略所有单指操作（只允许 `pointerup` 结束手势）。

### 4.3 会话期间不接受新事件源

手势进行中，必须屏蔽：
- 合成的 `wheel` 事件（见 §6）
- 长按识别器
- 双击检测

否则会出现"捏合过程中弹出上下文菜单"这类问题。

## 5. 提交时序：同步、原子、每帧一次

内核契约要求（来自 `viewportBus.ts` 与 `sharedViewportNotify.ts`）：

> - 提交是**同步**的：滚动事件在浏览器 paint 前触发，只有同步派发才能保证 sticky 图层与原生滚动的 DOM 内容层落在同一帧。**任何 rAF / 微任务延迟都会造成可见的一帧以上错位。**
> - `scrollLeft` 与 `pxPerSec` 必须**同帧一起送达，不能拆成两次**。

实现要求：
1. 在 `pointermove` 回调里**同步**调用 `setViewport` / `setRowHeightAndScrollTop`，**不要**用 rAF 节流。
2. `pointermove` 本身可能一帧触发多次 → 用一个 `pending` 标记合并：只在同一帧内允许最后一次提交生效，但**提交动作本身仍是同步的**（内核内部会做"值未变则跳过"的去重，见约束 3："滚轮亚像素噪声不得触发空重绘"）。
3. **一次手势回合内，水平与竖直各只调用一次写入口**：
   - 水平：`setViewport({ pxPerSec, scrollLeft })` —— 一次
   - 竖直：`setRowHeightAndScrollTop(rowHeight, scrollTop)` —— 一次
4. 写完不要立刻 `get()` 回读做二次修正——注释明确警告："外部不得再钳制，也不得依赖「写入后回读被修正的值」"。需要真值就用写入口的返回值（`setViewport` 返回提交后的状态）。
5. 宿主尺寸/轨道数变化后要 `reclamp()`（例如捏合过程中删除轨道、软键盘弹出改变高度）。

## 6. 与 Android WebView 的 wheel 合成路径的冲突

Chromium/Android WebView 会把多点手势**合成为 `wheel` 事件**（双指捏合 → `wheel` 且 `ctrlKey === true`；双指拖动 → 普通 `wheel`）。而 `wheelGesture.ts` 已经实现了触摸板手势识别，且内核已经在消费 wheel。

**这就是"缩放中心为两指中点"可能免费成立的另一半原因**：Chromium 合成的 wheel 事件**在手指中点位置派发**，而现有的"以指针为锚点缩放"路径取的就是事件坐标。所以理论上**什么都不做，Android 上的双指捏合就已经是"以两指中点为锚点"**。

但**绝不能让两条路径同时生效**（会双重缩放）。M0 必须实测并二选一：

| 路线 | 做法 | 优点 | 风险 |
| :--- | :--- | :--- | :--- |
| **(a) 复用 wheel 合成** | 什么都不改，让 WebView 的合成 wheel 喂给现有 `wheelGesture` 路径 | 零代码；锚点天然是中点 | ① WebView 的合成行为未在文档中承诺，可能随版本变 ② 只有水平/竖直的单轴 zoom 语义（Ctrl+wheel = 水平缩放），**拿不到"两轴独立缩放"** ③ 可能与 `touch-action` / `overscroll-behavior` 打架 ④ 拿不到平移的手指中点语义 |
| **(b) 自己实现手势层** | 监听 Pointer Events，按 §2–§5 对接内核；`touch-action: none` + 屏蔽合成 wheel | 完全可控；**才能真正做到"纵横两轴独立缩放与平移"**；锚点语义由我们保证 | 需要写手势状态机（约 300 行） |

**建议：以 (b) 为主**。因为你的需求是**两轴独立**，而 wheel 合成路径的语义是"Ctrl+wheel = 水平缩放"，拿不到竖直轴的独立控制。做法：

1. 在可交互画布上设 `touch-action: none`；
2. 手势层接管 `pointerdown/move/up`；
3. **在手势进行中屏蔽合成的 wheel**（`{ passive: false }` + `preventDefault()`，或在 wheel 处理器里判定"当前有 2+ 活跃指针就忽略"）；
4. **滚轮路径保留给桌面**（`IS_ANDROID` 分支，桌面一行不改，符合 ADR-005）。

M0 的实测清单（同时给出 (a)/(b) 的取舍依据）：
- 真机上双指捏合是否真的产生 `ctrlKey=true` 的 wheel？
- 该 wheel 的 `clientX/clientY` 是不是手指中点？
- 它的 `deltaY` 量级与桌面滚轮是否同一数量级？
- `touch-action: none` 是否会让合成 wheel 消失？

## 7. 三个待确认 / 待新增的点

| # | 事项 | 状态 | 说明 |
| :--- | :--- | :--- | :--- |
| 1 | 参数面板的**水平** pxPerSec 是"自己持有"还是"跟随时间轴" | **待确认** | `PianoRollPanel.tsx` 既有 `pianoRollViewportBus.emit(...)` 的两处调用，也消费时间轴的帧通知。需要确认在"参数面板内捏合"时应该写哪个真值，避免两个面板互相打架（`shouldNotifySharedViewport` 这个缺陷记录说明历史上就出现过这类问题） |
| 2 | 参数面板的**参数轴纵向缩放**入口 | **待新增** | 它不走 `rowHeight`（参数编辑器不涉及行高）。需要找到参数面板自己的"参数轴像素/单位比例"真值与写入入口；若没有，需要按 `scrollKernel` 的模式补一个（含"缩放+位置原子提交"，否则会复现同样的漂移振荡缺陷） |
| 3 | `rowHeight` 的上下限 | **待定义** | `scrollKernel` 未见对 `rowHeight` 做范围钳制。需与 `TrackList` 的行高拖拽手柄共用同一组常量（建议 28–240 CSS px） |

## 8. 验证方案

### 8.1 单元测试（可进 CI，与真机无关）

`scrollKernel` 已有 `scrollKernel.test.ts`，其中**已经包含纵向缩放的锚点测试**（第 243 行：`setRowHeightAndScrollTop(nextRowHeight, unit * nextRowHeight - pointerY)`）。照它的风格给手势层加：

| 用例 | 断言 |
| :--- | :--- |
| 纯竖直平移（kx=ky=1，mid 下移 Δ） | `scrollTop` 变化量 == Δ，`pxPerSec`/`rowHeight` 不变 |
| 纯水平平移 | `scrollLeft` 变化量 == Δ |
| 纯水平缩放、中点不动 | 中点下的秒数**不变**（误差 < 1e-9 秒） |
| 纯竖直缩放、中点不动 | 中点下的行号**不变** |
| 复合（平移 + 双轴缩放） | 中点下的 (秒, 行号) 均不变 |
| pxPerSec 被上限截断时 | 锚点仍不漂（证明"先 clamp 再算 scrollLeft"正确） |
| 死区：分离度变化 < 16 px | `pxPerSec`/`rowHeight` 全程不变 |
| 轴锁定：`span0.y < 24` | `ky` 恒为 1 |
| 状态机 `2→1` | 冷却期内的单指事件被忽略（空操作） |

**"中点下的内容不变"是这套实现的核心不变量，必须做成断言。**

### 8.2 真机 / 模拟器（CDP 注入多点触控）

用 `docs/05` 描述的 CDP 通道，`Input.dispatchTouchEvent` 支持多 `touchPoints`，可以精确脚本化：

```
双指平移    : 两点同向等距移动
水平捏合    : 两点 X 分离度线性变化、Y 不变
竖直捏合    : 两点 Y 分离度线性变化、X 不变
斜向捏合    : 两轴同时变化 + 中点位移
捏合后抬一指: 停 200ms 再抬第二指（验证冷却期）
```

每次操作后读内核真值（可经调试钩子暴露 `kernel.get()`）并断言 §8.1 的不变量。
