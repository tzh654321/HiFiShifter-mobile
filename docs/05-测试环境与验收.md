# 05 · 测试环境与验收方案

> 目标：让"改对没改对"这件事**可量化、可复跑**，而不是靠"看起来没问题"。
> 原则：**先把环境搭起来，再动代码**。这份文档的执行应排在 02 文档的改造之前。

## 1. 四层测试环境（各司其职）

| 层 | 环境 | 跑什么 | 成本 | 反馈速度 |
| :--- | :--- | :--- | :--- | :--- |
| **L0** | 桌面 Chrome（Vite dev server + IPC 桩） | 纯前端：排版、响应式断点、手势逻辑（用 Chrome DevTools 的触摸模拟） | 极低 | 秒级 |
| **L1** | Android 模拟器（AVD） | 集成：WebView 真实行为、多点手势合成、SAF、权限流程 | 中 | 1–3 分钟 |
| **L2** | 真机（主力机型） | 真实性能、真实音频、真实触感、挖孔/手势条 | 低 | 30 秒 |
| **L3** | 多机型矩阵 + CI | 回归：跨屏型、跨 Android 版本、跨 ABI | 高 | 小时级 |

**关键点：L0 一定要有。** 上游前端有 10.4 万行，绝大多数排版改动不需要真机。给 Vite 加一个 IPC 桩（`frontend/src/services/invoke.ts` 里已有 `window.__TAURI__` 探测逻辑，加一个"无 Tauri 时的 mock"分支即可），就能在桌面 Chrome 里按 360 × 800 调排版，效率比模拟器高一个数量级。

## 3. 各层环境的具体配置

### L0 · 桌面 Chrome（前端专用）

```bash
npm --prefix frontend install
npm --prefix frontend run dev     # → http://localhost:5173
```

改造点（一次性）：
- `frontend/src/services/invoke.ts` 增加 mock 分支，返回固定的假数据（工程、轨道、音频块、参数曲线）。
- `frontend/index.html` 的 viewport 加上移动端参数后，桌面 Chrome 用 **DevTools → Toggle Device Toolbar → 自定义尺寸 360×800 + Touch 模拟** 即可接近真机。
- 在 `App.tsx` 的外壳判定里加一个 `?forceMobile=1` 查询参数，强制走移动端布局，方便反复对比。

**限制**：Chrome 桌面模拟的触摸**不产生**"双指捏合合成 wheel"行为（那是 Android WebView 特有的），所以 `wheelGesture` 相关的手势验证必须上 L1/L2。但按 [08 文档](08-双指手势与视口内核对接规范.md) 的决策，**Android 走自己实现的手势层而非 wheel 合成路径**，因此手势层的**数学与状态机可以完全在 L0 用单元测试覆盖**（见 08 文档 §8.1），L0 的价值反而更高了。

### L1 · Android 模拟器

> ### ⚠️ 2026-09-18 实测更正：arm64 镜像在 x86_64 宿主上**根本起不来**
>
> ```
> FATAL | Avd's CPU Architecture 'arm64' is not supported by the QEMU2 emulator on x86_64 host.
>         System image must match the host architecture.
> ```
>
> 不是"慢"，是模拟器直接拒绝启动（Google 已取消 x86 宿主对 arm 镜像的跨架构模拟）。
> `emulator -accel-check` 显示 WHPX 10.0.26100 可用，但 WHPX 只能加速 **x86/x86_64** 镜像。
>
> **因此 L1 的形态改为**：**x86_64 镜像 + 本地临时的 x86_64 debug 构建**
> （`npx tauri android dev --target x86_64`，WHPX 加速，可用）。
> 这份 x86_64 包**只用于本地调试，绝不进发布产物** —— 发布仍严格 arm64-only（ADR-009）。
>
> 代价：**arm64 的真实行为（音频、性能、ABI、OOM 阈值）只能在真机验证**，
> 模拟器不能替代 L2。

- 模拟器的音频输出走宿主，**采样率/延迟与真机不同**，音频验收必须在真机做。
- 模拟器有 `x86_64` 版本（跑得快），但**真机是 arm64-v8a**——`libonnxruntime.so` 与 cpal/Oboe 需两个 ABI 都出包，否则模拟器上测不了。建议 AVD 用 arm64 镜像（慢但一致），x86_64 只用于纯 UI 测试。

### 4.1 WebView 调试（前端问题的主力手段）

Tauri 的 Android WebView 在 **debug 构建**下是可调试的。你有现成的 CDP 调试经验（重力四子棋项目就是这套），流程一致：

#    chrome://inspect   → 应能看到 WebView 目标

Android 上 `std::eprintln!` 会进 `logcat`（Tauri 会转发 stdout/stderr）。建议：
- 上游的 `debug_eprintln!` 宏（定义在 `lib.rs` 顶部，release 下编译掉）已经做了这个设计，**Android debug 构建直接可用**。

### 5.2 前端 / UI 自动化（排版验收的核心）

用 **Playwright + CDP 连接真机/模拟器里的 WebView**，把 04 文档的验收标准写成断言：

```ts
// 伪代码：接上 WebView 后跑一组排版断言
const browser = await chromium.connectOverCDP('http://localhost:9222');
const page = browser.contexts()[0].pages()[0];

// ① 无横向溢出
expect(await page.evaluate(() =>
    document.documentElement.scrollWidth <= document.documentElement.clientWidth
)).toBe(true);

// ② 扫描所有可见元素是否越界（"被遮挡/显示不全"的机械检测）
const overflow = await page.evaluate(() => {
    const out: any[] = [];
    document.querySelectorAll('*').forEach(el => {
        const r = (el as HTMLElement).getBoundingClientRect();
        if (r.width === 0 || r.height === 0) return;
        if (r.left < -1 || r.right > innerWidth + 1 || r.top < -1 || r.bottom > innerHeight + 1) {
            out.push({ tag: el.tagName, cls: (el as HTMLElement).className, r });
        }
    });
    return out;
});
expect(overflow).toEqual([]);

// ③ 可点目标 ≥ 44px
const tooSmall = await page.evaluate(() => {
    const out: any[] = [];
    document.querySelectorAll('button,[role=button],[data-clickable]').forEach(el => {
        const r = (el as HTMLElement).getBoundingClientRect();
        if (r.width === 0) return;                       // 跳过隐藏元素
        if (r.width < 44 || r.height < 44) out.push({ cls: (el as HTMLElement).className, w: r.width, h: r.height });
    });
    return out;
});

// ④ 字号下限
const smallFont = await page.evaluate(() => {
    const out: any[] = [];
    document.querySelectorAll('*').forEach(el => {
        const s = parseFloat(getComputedStyle(el as HTMLElement).fontSize);
        const hasText = (el.textContent || '').trim().length > 0 &&
                        el.children.length === 0;
        if (hasText && s < 12) out.push({ cls: (el as HTMLElement).className, s });
    });
    return out;
});
```

这套脚本的价值：**把"有没有显示不全/被遮挡/按钮太小"从主观判断变成可复跑的清单**，而且能在每个屏型上跑一遍。建议把它做成 `scripts/layout-audit.mjs`，每次改动后跑一次，输出「越界元素 / 过小按钮 / 过小字号」三张清单。

### 5.3 多点触控的手势回归

CDP 的 `Input.dispatchTouchEvent` 支持多 `touchPoints`，可以精确模拟：
- 双指平移（两个点同向移动）
- 双指捏合（两点相向/背向移动）
- 长按（按下 → 停 400 ms → 抬起）
- 手指数变化（1→2→1）

把它写成一组固定手势脚本，用来回归 03 文档的验收标准 4（"单指绘制不被双指手势污染，连续 100 次无脏状态"）。

**双指两轴手势的专项回归**（依最新需求，规范见 [08 文档](08-双指手势与视口内核对接规范.md)）——每项都要断言 **"两指中点下的内容不变"** 这个核心不变量：

| 脚本 | 断言 |
| :--- | :--- |
| 双指同向等距移动（水平 / 竖直） | 滚动量 == 手指位移；`pxPerSec` / `rowHeight` 完全不变 |
| 水平捏合（X 分离度变化，Y 不变） | 中点下的**秒数**不变；`rowHeight` 完全不变 |
| 竖直捏合（Y 分离度变化，X 不变） | 中点下的**行号**不变；`pxPerSec` 完全不变 |
| 斜向捏合 + 中点位移 | 中点下的 (秒, 行号) 均不变，两轴各自正确 |
| 捏合后抬一指，200 ms 后抬第二指 | 冷却期内无任何单指副作用 |
| 连续 20 次纯双指拖动 | 误缩放次数 == 0（验证死区） |
| 时间线上捏合 | 参数面板的 `pxPerSec` **同步变化**（验证共享视口契约） |

调试钩子：把 `kernel.get()` 挂到 `window.__hsKernel` 之类的调试对象上（上游已有 `__hsPianoRollKernel` 的先例），供脚本读取真值断言。

## 6. 性能与资源基准（移动端的真实风险）

> **好消息（依 Q7 核实结果）**：`develop` 已经包含完整的 WebGL2 渲染内核与**离线性能基准**，性能风险显著低于初评。
> 直接可用：`npm --prefix frontend run bench`（= `vitest bench`，跑 `waveform/waveformPerf.bench.ts`），它测的是「10 轨 / 400 clip / 全览缩放」下的 scene 构建 → geometry 构建 → 线段展开三段耗时，**纯函数、不依赖 DOM/WebGL，可在 Node 下跑、可进 CI**。
> 用法：桌面先取基线，真机再取一次，对比 GPU 实际绘制帧时间。

| 关注点 | 工具 / 命令 | 通过标准（建议） |
| :--- | :--- | :--- |
| 渲染三段耗时（离线） | `npm --prefix frontend run bench` | 桌面基线 × 2.5 以内（arm64 中端机粗估） |
| 内存峰值 | `adb shell dumpsys meminfo com.arounder.hifishifter` | 加载全部模型后 PSS < 1.2 GB；不因 OOM 被杀 |
| 冷启动时间 | `adb shell am start -W -n <pkg>/.MainActivity` | 首屏 < 3 s（首次，含模型拷贝）；之后 < 1.5 s |
| 首次模型拷贝 | 探针 3 的实测 | 记录基线数值，写入 README |
| UI 帧率 | `adb shell dumpsys gfxinfo <pkg> framestats` | 时间线滚动/缩放时 90 分位帧时间 < 16 ms（60 fps） |
| **双指手势流畅度** | 同上 + 手势脚本 | 捏合/平移过程中无掉帧尖峰、无"内容漂移"（漂移是 08 文档明确要防的缺陷） |
| 音频欠载 | `dumpsys media.audio_flinger` 的 underrun 计数 | 播放 3 分钟，underrun = 0 |
| 推理耗时 | 应用内计时日志 | NSF-HiFiGAN 单块推理记录真机数值（用于决定是否需要量化模型） |
| 电量/温度 | `adb shell dumpsys battery` | 长任务（hnsep 分离）时观察温升与降频 |

**必须在 M0 探针阶段就拿到基线数字**，否则后期无法判断"卡"是回归还是本来就这样。

## 8. 验收流程（每个里程碑跑一遍）

## 8.5 逐项功能验收：模拟输入 + 四级降级（**最终验收的判定方式**）

### 验收方式

每个功能都必须用**模拟点击 / 划动 / 多指**操作一遍，每项判定**两件事**：

1. **看得到** —— 控件在可视区内，没有被系统栏 / 相邻面板 / 自身溢出裁掉；
2. **点得到** —— 模拟输入落点能命中它，且命中后行为正确。

**两者同时成立才算通过。「截图里看起来有」不算通过** —— 桌面 UI 搬到小屏最容易出现的
不是"没画出来"，而是画出来了但**在可视区外 / 被覆盖 / 命中区偏移**，只有模拟输入能证伪。
（同理，"能点到"也不等于"看得见"：被系统栏压住的控件仍可能接受点击。）

判定要用**客观量**，不要靠肉眼：控件矩形落在可视区内、命中点落在控件矩形内、
以及操作前后的状态变化。`docs/12` 那类分时截图只用于**定位**，不能作为通过依据。

### 放不下时的四级降级（按此顺序尝试）

| 级别 | 做法 | 适用场景 |
| :--- | :--- | :--- |
| **1. 调排版** | 先看屏幕**哪部分比较空** —— 优先把控件挪进空白区，而不是先缩字号 | 局部拥挤、有明显留白 |
| **2. 折叠进菜单** | 把**平铺**的次要按键收进菜单 / 溢出菜单 | 一排按键太多、单排挤不下 |
| **3. 略缩字号** | 只做**小幅**缩小 | 前两级不够，且缩后仍 ≥ 正文下限 |
| **4. 图标化** | 用**图标化控件**替代「文字 + 传统样式控件」 | 文字占位过大、或语义有公认图标 |

**不可违反的约束**（与 `docs/07` 的决策一致）：**触摸目标 ≥ 44 px、正文字号 ≥ 16 px**。
若第 4 级做完仍不满足，说明该功能的**信息架构**要重做，而不是继续压字号。

**降级是局部手段**；全局仍按 `docs/07` 的三套布局（`phone` < 600 / `tablet` ≥ 600 且 ≥ 500 高 /
`desktop` ≥ 1280）分档，**平板不复用手机布局**。

### 需要的工具

| 工具 | 作用 | 状态 |
| :--- | :--- | :--- |
| `scripts/layout-audit.mjs` | 经 CDP 取每个交互元素的矩形，输出「越界 / 被祖先裁掉 / 被遮挡 / 命中区 < 44 px」清单 | ✅ 已实现（见 `docs/13`） |
| `scripts/touch-drive.mjs` | 经 CDP `Input.dispatchTouchEvent` 做点击 / 划动 / 双指缩放 / 双指平移，并输出前后状态摘要 | ✅ 已实现（见 `docs/13`） |
| `scripts/lib/cdp.mjs` | 零依赖 CDP 客户端（Node 22 自带 `fetch` + `WebSocket`） | ✅ 已实现 |
| `scripts/measure-inset.py` | 量「系统栏有没有压住内容」（像素位移搜索 + 条带残留计数） | ✅ 已实现 |
| `run-app.sh --shots` | 分时截图，用于**定位**问题发生在哪个阶段（不用于判定通过） | ✅ 已有 |

多指必须走 CDP（`Input.dispatchTouchEvent` 支持多 `touchPoints`）；
`adb shell input` 做不了双指 —— 这一点 `docs/08` 已定，视口改动一律走 `scrollKernel` 原子入口。

> ⚠️ CDP 的触摸坐标是 **CSS px、相对 WebView 视口**，与 `layout-audit.mjs` 输出的
> `rect` 同一套坐标系，**不是**截图的设备像素（差 `devicePixelRatio` 倍）。
> 两个脚本都会对超范围坐标给出警告。

## 附：构建流水线会把原生库截成 0 字节（2026-09-22，根因已定位 + 自动修补）

### 症状（最阴的一点：构建**一切正常**）

```
BUILD SUCCESSFUL / Finished 1 APK / exit 0
```

装到设备上**启动即崩**：

```
java.lang.UnsatisfiedLinkError: dlopen failed:
  ".../base.apk!/lib/x86_64/libbackend_lib.so" has bad ELF magic: 504b0304
  at com.arounder.hifishifter.WryActivity.<clinit>(WryActivity.kt:130)
```

`504b0304` 是 ZIP 头（`PK\x03\x04`）—— 说明那个条目根本不是 ELF，而是**空/错内容**。

### 根因（2026-09-22 第二轮用对照实验钉死）

`tauri android build` 在打包期间把 `libbackend_lib.so` 与 `libc++_shared.so`
**symlink** 进 `gen/android/app/src/main/jniLibs/<abi>/`（日志里 `Info symlinking lib ...`，
一次构建出现**两轮**）。而本机上"symlink"这个调用**产出的不是链接，是一个 0 字节普通文件**：

- 源文件是好的：`D:/hfshifter-target-upstream/x86_64-linux-android/debug/libbackend_lib.so`
  = 76 MB ELF；
- jniLibs 里却是 `0` bytes；
- `fs.symlinkSync(src, dst)` **不抛错**，但 `lstat(dst).isSymbolicLink() === false`、
  `readlink` 报 `EINVAL` —— 造出来的根本不是链接，所以 tauri 认为"成功了"。

**真因是机器级的权限缺失**，不是沙箱、不是垫片、不是文件系统：

| 对照实验 | 结果 |
| :--- | :--- |
| Node 探针，**沙箱内** | `ok` + 0 字节普通文件 |
| Node 探针，**沙箱外**（`dangerouslyDisableSandbox`）| **一模一样** ⇒ 与沙箱策略无关 |
| `env -u NODE_OPTIONS -u PYTHONPATH` 再跑 | **一模一样** ⇒ 与那两个垫片注入无关 |
| Python `os.symlink` | 同样 `ok` + 0 字节 |
| 目标改到 C 盘（两盘都是 NTFS）| 同样 ⇒ 与文件系统无关 |
| **PowerShell 原生 `New-Item -ItemType SymbolicLink`** | **`THREW: 此操作需要管理员权限`** |

```powershell
HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock\AllowDevelopmentWithoutDevLicense = 0
isAdmin = False     # LAPTOP-N0JJ7QQ4\tzh 不在管理员组
```

⇒ Windows 创建符号链接需要 `SeCreateSymbolicLinkPrivilege`，默认只有管理员持有，
普通用户要靠**开发人员模式**才拿到。本机两样都没有，内核直接拒绝创建链接；
而 Node / Python 在此环境下**不抛错**，把失败降级成"创建了一个空文件"。

与 **ABI 切换**强相关：`sync-native-libs.sh` 会清掉"本次不需要"的 ABI 目录，
下次为那个 ABI 构建时 jniLibs 里没有目标文件 ⇒ 走 symlink 分支。

> **一劳永逸的修法（要用户操作，一次即可）**：Windows 设置 → 系统 → 开发者选项 →
> **开发人员模式 = 开**。开了之后 `tauri android build` 自己就会产出正确的库，
> 下面的 ③ 可以退居纯兜底。判定与复现用 `node scripts/_probe-symlink.mjs <src> <dst>`。

### 防护（`docs/14` 的"删除进回收站"同款思路：不靠记住，靠拦住）

| 层 | 位置 | 作用 |
| :--- | :--- | :--- |
| ① 检出 + **自动修补 + 复验** | `build-apk.sh §⑧` | 逐个校验 APK 里 `lib/**/*.so` 是**非空 + `\x7fELF`**；不合格时**自动调用 ③**，再复验，仍不合格才 `exit 3`。⇒ `bash scripts/build-apk.sh <abi>` **一条命令就能拿到可安装的包** |
| ② 打包前补真文件 | `build.gradle.kts` 的 `HS-NATIVE-LIB-FIX`（由 `setup-gen-android.sh §9` 注入，幂等）| 注册 `hsFixNativeLibs` 并 `dependsOn` 到 `merge*JniLibFolders`；**只补"不存在或 0 字节"的**（绝不覆盖正常文件）|
| ③ 产物级修补 | `scripts/fix-apk-native-libs.sh <apk> [abi]` | 直接替换 APK 里的空条目 → `zipalign -p 4`（未压缩 .so 需页对齐）→ `apksigner` 重签（debug keystore）|

⚠️ 实测 ②**不足以**兜住：截断在"合并 jniLibs 之后、打包之前"还有一次，所以真正兜底的是 ③。
②③ 都不改 Rust 产物，**秒级**完成。
