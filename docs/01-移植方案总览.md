# 01 · 安卓移植方案总览

---

> ## 📌 2026-09-18 更新摘要（Q1–Q7 已闭环 + 两处核实纠正）
>
> **决策已定**（详见 [06 文档 ADR-006 ~ ADR-013](06-风险登记与决策记录.md) 与 [07 文档](07-决策落地与FLM式自适应布局.md)）：

> - 第一版不做后台播放；**仅出 `arm64-v8a`**；**minSdk 26**；建真 fork（凭据操作由你执行）
>
> **两处纠正（核实后推翻初版结论）**：
> 1. **不需要从任何上游分支摘代码。** `develop` 已自带完整 WebGL2 渲染内核（`renderKernel/gl/*` + `waveform/surfaceRenderer` + 字形图集管线），且已有**离线性能基准** `waveformPerf.bench.ts`（`npm run bench`）。`feature/timeline-unified-render-kernel` 也已并入。详见 [00 文档 §2](00-上游调研与分支盘点.md) 与 [07 文档 §4.1](07-决策落地与FLM式自适应布局.md)。

>
> **这两条把本项目的风险与工作量都明显下调**：原本排在最大成本项的"交互层重写"里，视口手势这块基本变成接线工作。

## 1. 一句话结论

**走 Tauri 2 官方 Android 通道，保留 Rust 后端 + 复用 10.4 万行前端，只做"平台裁剪 + 交互层适配 + 多形态排版"三类改动。** 不需要重写音频引擎，也不需要把算法搬去 Java/Kotlin。

## 2. 技术路线选型

| 方案 | 做法 | 优点 | 致命问题 | 判定 |
| :--- | :--- | :--- | :--- | :--- |
| **A. Tauri 2 Android（推荐）** | `cargo tauri android init/build`，Rust 编译到 `aarch64-linux-android`，前端原样进 WebView | 复用 100% 算法代码、100% 前端组件；上游持续更新可直接 rebase；单一技术栈 | 需要解决 cpal/Oboe、ORT/Android、184 MB 模型加载、SAF 文件访问四件事 | ✅ **选它** |
| B. 纯 Web / WASM 化 | 把 Rust 逻辑编译成 WASM，套壳 Capacitor | 无 NDK 编译链 | Rust 代码深度依赖 `std::thread` / rayon / 文件 IO / cpal，WASM 化等于重写；ORT 的 WASM 后端性能无法接受 | ❌ |
| C. 原生 Android UI + Rust 核心 JNI | Kotlin UI，Rust 做 `cdylib` 经 JNI 暴露 | UI 手感最原生 | 10.4 万行 React 组件全部作废，等于从零做；时间不可控 | ❌ |

**A 方案的关键前提已被官方文档确认**：
- Tauri 2 的 Android 支持是正式能力（`tauri android init` 会生成 `gen/android` Gradle 工程）。
- Tauri 在 Android 上 `resource_dir()` 返回的不是文件系统路径，而是 **`asset://localhost/` 这种特殊 URI 前缀**（上游文档原文：*"Currently the resources are stored in the APK as assets so it's not a normal file system path, we return a special URI prefix asset://localhost/"*）。**这一条直接决定 184 MB 模型的加载方案必须重做**（见 §5）。

## 3. 功能裁剪表

原则：**只保留"手机上真能操作、真有意义"的功能**。下表每条都给判定依据。

### 3.1 必须移除（Windows 专属，无法移植）

| 功能 | 代码位置 | 移除理由 |
| :--- | :--- | :--- |
| **Vslib 算法（VocalShifter 库）** | `vocoder/vslib.rs`、`renderer/vslib_processor.rs`、`third_party/vslib/vslib_x64.dll`（1.4 MB） | 官方 `vslib_x64.dll` 只有 Windows x64 PE 版本，且只提供文件 IO 接口。上游自己给 Linux 打包时就是 `--no-default-features --features onnx`。**默认 feature 里必须去掉 `vslib`** |
| **VST 宿主集成** | `feature/vst-host-integration` 分支（未合并） | Android 无 VST 生态，不引入 |
| **WASAPI 录音回环（录系统声音）** | `recording/wasapi.rs`、`recording/capture.rs` 中 loopback 分支 | WASAPI 是 Windows 音频栈。Android 侧"录音"只用麦克风（`AudioRecord`/cpal 输入），系统内录在 Android 10+ 需要 `MediaProjection` 授权，成本高收益低 → **降级为"仅麦克风录音"** |
| **DirectML GPU 推理** | `vocoder/dml_adapters.rs`、`resources/DirectML.dll` | Windows 专属 |
| **原生菜单栏（MenuBar）/ 窗口装饰控制** | 前端 `components/layout/MenuBar.tsx`；Tauri `core:window:allow-set-decorations` 等权限 | Android 没有窗口标题栏与原生菜单栏概念（Tauri 官方文档亦确认移动端无菜单/无窗口装饰）。改为应用内汉堡菜单 |
| **第二窗口（AppearanceWindow）** | `AppearanceSettingsDialog.tsx` 里 `new WebviewWindow`、`core:webview:allow-create-webview-window` | Android 上多窗口是"Activity/多任务"语义，弹一个独立浮动窗口既不可控也不好用。改为**应用内全屏页 / 底部抽屉** |
| **REAPER / VocalShifter 工程的剪贴板互导** | `system_clipboard.rs`（`clipboard-win`）、`linux_clipboard.rs`（xcb/wl-clipboard）、`import/reaper_*`、`commands/reaper_clipboard.rs`、`commands/vocalshifter_clipboard.rs` | 依赖桌面剪贴板的 `REAPERMedia` / VocalShifter 私有格式，且需要配套桌面 DAW。**移除粘贴通道，保留"打开 .rpp / VocalShifter 工程文件"的导入能力**（文件导入在 Android 上可行） |
| **`--benchmark` / `--log-file` 命令行诊断** | `main.rs` | 无命令行入口。改为把日志写 `logcat`，基准测试移进设置页按钮 |
| **ffmpeg 视频支持（未合并分支）** | `feature/ffmpeg-video-support` | 显著增重，移动端不需要 |

### 3.2 保留但需要重做（逻辑能用，接口要换）

| 功能 | 桌面实现 | Android 实现 |
| :--- | :--- | :--- |
| 打开 / 保存 / 选择目录 | `rfd::FileDialog`（12 处） | `tauri-plugin-dialog`（Android 后端走 **SAF**，返回 `content://` URI）→ 后端需要 `content://` → 本地路径的落地拷贝 |
| 工程文件读写 | 直接 `std::fs` 绝对路径 | 应用私有目录可直接 fs；`content://` 需先拷到私有目录 |
| 音频/视频导入 | OS 拖拽（`dragDropEnabled: true` + `onDragDropEvent`） | 无 OS 拖拽。改为「导入按钮 → SAF 选择器」+ 应用内文件浏览器（`FileBrowserPanel` 已有，改造后可用） |
| 文本复制粘贴 | 桌面剪贴板 | `tauri-plugin-clipboard-manager` |
| 麦克风录音 | cpal 输入 | cpal 输入（Android 后端是 Oboe，同一套 API）+ 运行时 `RECORD_AUDIO` 权限申请 |

### 3.3 保留（算法与计算全部保留）

- 三种声码器中的 **WORLD** 与 **PC-NSF-HiFiGAN**（即 `--no-default-features --features onnx` 这一档）
- 音频解码（symphonia）、重采样（rubato）、时间拉伸（SoundTouch / Signalsmith）
- 全部音高分析与缓存体系（`pitch/`、`pitch_analysis/`）
- MIDI 导入导出（`midly`）
- 工程保存（`.hshp`）
- 184 MB ONNX 模型（但加载方式要改，见 §5）

## 4. 目标形态与产品决策

### 4.1 屏幕与形态

| 项 | 决策 |
| :--- | :--- |
| 目标设备 | **手机必须好用**（一等公民）；**平板不复用手机布局**，参照 FL Studio Mobile 走"可停靠多面板" —— 见 ADR-006 / ADR-007 |
| 主布局 | **三套并存**：`phone`（宽 < 600）= 单面板 + 底部页签（轨道/参数/文件/工程）；`tablet`（宽 ≥ 600 且高 ≥ 500）= 可停靠多面板 + 可拖分隔条 + 可折叠侧栏；`desktop`（≥ 1280）= 上游现有布局，一行不改 |
| 平板的硬约束 | 触摸目标仍 ≥ 44 px、正文仍 ≥ 16 px；差异只体现在**同屏面板数与信息密度**，**不得把控件/字号压到桌面尺寸**。详见 [07 文档 §2.2](07-决策落地与FLM式自适应布局.md) |
| 兜底方向 | 手机走页签互斥；若真机验证发现切换过于频繁影响效率，退回"可折叠分栏"（时间线可折到 1/3 高） |

### 4.2 版本节奏（里程碑）

| 阶段 | 目标 | 出口标准（可验证） |
| :--- | :--- | :--- |
| **M0 探针（Spike）** | 跑通「Tauri 空壳 + cpal 出声 + ort 加载模型」三个最小验证 | 三个 Demo 分别在真机上出结果：① 播放一段正弦波 ② 加载 `pc_nsf_hifigan.onnx` 并跑一次推理 ③ 从 assets 拷 184 MB 到私有目录并计时 |
| **M1 可启动** | 上游代码在 Android 上编译通过并启动到首屏 | `cargo tauri android build` 成功；APK 启动进入主界面不崩；`logcat` 无 panic |
| **M2 可编辑** | 能导入一个音频文件、放到轨道、拖动、切分、保存工程 | 真机上完整走通 README 的"工作流推荐"第 1–2 步 |
| **M3 可出声** | 能导出音频 + 能实时播放 | 导出的 wav 与桌面版**逐样本比对**一致（允许 ±1 LSB） |
| **M4 触控适配** | 03 文档的手势映射全部落地 | 无键盘/无右键/无滚轮可用；单指可完成桌面版 90% 的右键操作 |

### 4.3 仓库结构规划

```
HiFiShifter-mobile/
├── upstream-src/                  # 上游克隆（保持可 rebase，尽量不直接改）
├── android/                       # 【新增】移动端适配层，与上游解耦
│   ├── inject/                    #   WebView 注入脚本（手势层、视口、响应式开关）
│   ├── patches/                   #   对上游的最小补丁（.patch 文件，可脚本化重放）
│   └── README.md
├── docs/                          # 本方案文档集
├── scripts/
│   ├── apply-patches.sh           # 把 patches/ 重放到 upstream-src
│   ├── build-android.sh           # cargo tauri android build 封装
│   └── export-patches.sh          # 从 upstream-src 反向导出补丁
└── README.md
```

**为什么要 `patches/` 而不是直接 fork 改**：上游迭代很快（develop 一天多就 500 文件变化）。把改动隔离成可重放的小补丁，能让你随时 `git rebase` 到最新上游而不陷入冲突地狱——这也是"上游没做过移动端"这个现实下唯一可持续的姿势。

## 5. 四个必须提前决策的技术卡点

### 卡点 1：184 MB ONNX 模型怎么进 APK、怎么被 ort 读到

**问题**：Android 上 `resource_dir()` 返回 `asset://localhost/` 而非真实路径，而 ort 需要真实的 `libonnxruntime.so` / `.onnx` 文件路径。

**方案对比**：

| 方案 | 做法 | 评价 |
| :--- | :--- | :--- |
| 5-A 启动时从 assets 拷到私有目录 | Rust 侧用 JNI 拿 `AAssetManager`，流式拷贝到 `app_data_dir/models/`，用版本号标记避免重复拷贝 | ✅ **首选**。逻辑简单、ort 直接吃路径；代价是首次启动多占 184 MB 空间 + 一次拷贝耗时 |
| 5-B 前端 `fetch('asset://…')` + `plugin-fs` 分块写 | 绕开 JNI | 🔶 备选。184 MB 过 JS 层，内存与耗时风险高 |
| 5-C 首次启动下载 / 用户手动导入模型包 | APK 里不放模型 | ✅ **建议同时做**，与 5-A 并存：既解决 APK 体积，也给低配设备一个"只装 NSF-HiFiGAN、不装 hnsep"的选择 |
| 5-D 模型量化（int8）| 把 54/88 MB 压到 ~15/25 MB | 🔶 需验证音质损失是否可接受，属于优化项不是阻塞项 |

**决策建议**：M0 探针阶段就实测 5-A 的拷贝耗时；同时把模型做成"可缺省"——`hnsep.onnx` 缺失时自动禁用"气声/张力"编辑（上游已有 `is_available()` 降级分支，改动量小）。

### 卡点 2：cpal 在 Android 上能不能出声

**现状**：`cpal 0.15.3` 的 Android 后端是 **Oboe**（cpp 库）。社区在 Tauri 项目上有过成功记录，但踩了两个坑：

1. 必须显式开启 feature：`cpal = { version = "0.15.3", default-features = false, features = ["oboe-shared-stdcxx"] }`，否则运行时报 `dlopen failed: library "libc++_shared.so" not found`。
2. 需要确认 JavaVM/Activity 上下文（`ndk-context`）已被初始化。

**对策**：
- 首选：按上面的 feature 配置 + 在 `tauri::Builder::setup` 里确保 NDK 上下文可用。
- 备选 A：升级到 cpal 0.16+（新 Android 后端改为 **AAudio**，不再依赖 C++ 运行时的 `libc++_shared`）。
- 备选 B：Android 专属分支直接调 **AAudio**（`oboe` crate 或 `aaudio` sys 绑定）实现 `build_output_stream` 的等价物，仅约 200 行——`audio_engine/engine.rs` 已经把输出抽象成"给一个 f32/i16 回调"的形状，替换面很小。

> 这是**最高优先级**的验证项，M0 阶段第一件事。

### 卡点 3：ORT 在 Android 上的二进制

**现状**：Windows 用 `ort` + `directml` + `download-binaries`（编译期自动下载）。

**Android 方案**（推荐，改动最小）：
1. `ort` 改为 `features = ["std", "ndarray", "load-dynamic"]`，**不启用** `download-binaries`。
2. 从官方 `onnxruntime-android` AAR（含 `arm64-v8a` / `armeabi-v7a` / `x86_64` 的 `libonnxruntime.so`）取出 so，放进 `gen/android/app/src/main/jniLibs/<abi>/`。
3. 在 `run()` 启动最早期调用 `ort::init_from(<libonnxruntime.so 路径>).commit()`，路径通过 `System.loadLibrary` 或绝对路径解析。

**性能预期**：Android 上没有 DirectML，首选 **NNAPI / XNNPACK** EP；`ort` 已提供 `nnapi` feature。若 NNAPI 在目标机型上不稳定（常见），退回 **CPU EP + `rayon` 多线程**，并在设置页保留"推理设备"选择（上游 `commands/ui_settings.rs` 里已有 `update_ort_ep` 的接口形状）。

### 卡点 4：`content://` 与文件系统

Android 的 SAF 返回 `content://` URI，不是路径。而整个 Rust 侧是路径驱动的（`symphonia` 读文件、工程引用源文件路径、184 MB 模型的路径）。

**对策**：
- 新增一层 `resolve_input_path(uri_or_path) -> PathBuf`：若是 `content://`，用 `ContentResolver` 打开流并拷进 `cacheDir/imports/<hash>.<ext>`，返回真实路径。
- **注意工程引用语义**：桌面版工程保存的是"源文件绝对路径"。Android 上应改为「保存已导入的私有副本路径 + 原始显示名」，否则工程换机器就失效。这是**数据格式的兼容性决策**，建议在 `.hshp` 里加一个 `platform` 字段与 `portable: true` 标记，保持向后可读。

| **渲染性能** | 上游已完成 | ~~★★★~~ → **★** | ⬇️ **下调**：`develop` 已自带 WebGL2 内核 + 离线基准，见 [07 文档 §4.1](07-决策落地与FLM式自适应布局.md) |
| 触控交互层其余部分（右键 45 / 鼠标键 61 / 键盘 115 / hover 116 的替代入口） | 量大且需要设计判断 | ★★★★★ | 不变（仍是最大工作量） |

> 触控与排版两项合计仍是本次移植的主要成本，后端改造反而是相对确定的部分。这也说明：**这是"UI 适配项目"，不是"音频算法移植项目"**。
> 好消息是两个原本的重灾区（视口手势的数学、渲染性能）经过核实都不需要我们做——前者内核已备好原子入口，后者上游已经把渲染 GPU 化并给了离线基准。
