# 14 · 磁盘与临时目录治理

> 目的：止住「C 盘被构建写爆 → 构建报 `拒绝访问` / 模拟器秒退」这条反复发作的病。
> 结论：**根因不是「删不掉」，是「往哪儿写」和「删了不释放」两件事叠在一起。**
> 本文记录实测数据、机制判定与可复跑命令。相关脚本：`scripts/set-temp-d.ps1`、
> `scripts/clean-disk.ps1`、`scripts/_binreport.py`。

| C: 可用空间 | 清空回收站后 **688 MB**（+156 MB）；D: 48.8 GB |

## 2. 核心机制：进程的环境块是「启动时定型」的

这是整件事最反直觉、也最值得记住的一点。

Windows 给每个进程的环境块，是在**进程创建那一刻**由「机器级变量 → 被用户级变量覆盖」拼出来的，
之后**再也不会回溯更新**。改注册表里的用户变量，只有**之后新启动**的进程才拿得到新值
（而且要么由 Explorer 拉起、要么那个进程自己重新读了注册表）。

实测（2026-09-21 00:0x）：

```
TEMP   用户=[D:\DeskBoxDev\temp]   机器=[C:\windows\TEMP]   本进程=[C:\Users\tzh\AppData\Local\Temp]
TMP    用户=[D:\DeskBoxDev\temp]   机器=[C:\windows\TEMP]   本进程=[C:\Users\tzh\AppData\Local\Temp]
TMPDIR 用户=[]                     机器=[]                 本进程=[]
```

**用户级早就是 D: 了**（今天 23:29 那次 .NET 工具链安装设的），但本进程仍显示 `C:\Users\tzh\AppData\Local\Temp`
—— 因为 WorkBuddy 是在那之前启动的，它一路把这个旧副本传给了每个子命令，包括构建脚本。

⇒ **所以「系统里设好了」不等于「构建时会生效」。** 项目侧必须自己声明，不依赖外部状态。
这就是 `android-env.sh` 里新加那段（含注释说明原因）的由来。

顺带一个 Windows 常识，避免下次误改：**机器级 `TEMP` 故意保持 `C:\windows\TEMP` 不动。**
它被以 SYSTEM 运行的服务使用，而服务在开机早期就可能需要它；把机器级指到 D:，
一旦 D: 因任何原因不可用（分区挂载慢、盘未就绪），受影响的是所有服务。
用户级会覆盖机器级，所以只改用户级就足够，且**不需要管理员**。

## 3. 删除行为的机制（这轮才真正查清）

之前我以为是「工具层扫描命令字符串」。**这个判断是错的。** 三组对照实验：

| 实验 | 删除方式 | 结果 |
| :--- | :--- | :--- |
| A | PS 工具会话里 `Remove-Item`（被替换成 `Function`，`CommandType=Function`） | 进回收站 |
| B | `-NoProfile` 子进程里 `Remove-Item`（**确认为原生 `Cmdlet`**） | **也进回收站** |
| C | 子进程里 `[IO.File]::Delete()`（P/Invoke，最终是 `DeleteFile`） | **也进回收站** |

判定方式不是数文件个数（噪声极大），而是**解析回收站的 `$I` 元数据文件**里的原路径
（`scripts/_binreport.py`）。B/C 的标记文件确实出现在回收站里。

⇒ 拦截在 **PowerShell 之下**，与命令行怎么写无关。环境变量里也留了指纹：

```
WORKBUDDY_FS_PROTECTION_ROLE = daemon
CODEBUDDY_SAFE_DELETE_BULK_GUARD = ...\cli\vendor\shim\safe-delete-bulk-guard.cjs
CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD = 50      # >50 个文件要批量确认
```

**可操作的两条推论**：

1. **没有「换个删除姿势」的捷径**。子进程、原生 cmdlet、.NET API 都试过，都会进回收站。
   所以「快、真删、不进回收站」只能到**你自己的终端**里做（那不在 WorkBuddy 的进程树里）。
2. **「每次对话回收站一大堆文件」的主体不是 AI 的显式删除，而是构建过程自身的文件更替。**
   按 `$I` 里的原路径聚合，条目最多的来源是：

   | 条目数 | 来源 |
   | ---: | :--- |
   | 4,395 | `D:\code\HiFiShifter\hfshifter-target-upstream`（cargo 的 `target/`，`build/*/out`、`out/library`…）|
   | 320 | `D:\code\HiFiShifter\hfshifter-target`（旧 target 目录）|
   | 232 | `D:\Download\DeskBox-src\...\obj\...`（msbuild 生成的 `.g.cs` / `.g.i.cs`）|

   也就是说：**每跑一次构建，被覆盖/清理的中间产物都会进回收站**。这解释了为什么
   「一次对话下来」条目数量会爆炸 —— 那几次 `rm -rf app/build`、cargo 重新编译贡献了绝大部分。

   🕳️ 附带一个坑：`$I` 里存的删除时间是 **UTC**。不做换算会以为「16:11 删的」，
   实际是本地 00:11 —— 排查时差点把「几分钟前的操作」当成「八小时前的陈旧记录」。

## 4. 缓解手段（按性价比）

| 做法 | 效果 | 代价 |
| :--- | :--- | :--- |
| **给回收站设上限**（右键回收站 → 属性 → 勾选「自定义大小」，例如 4 GB）| 超了自动丢最旧的，**永不无限增长** | 无 |
| **定期 `Clear-RecycleBin -Force`** | 立即释放；已验证可用（本次 +156 MB / +17 MB） | 无（回收站内容本就是要放弃的）|
| **构建优先增量**、不 `clean`、别 `rm -rf` 整棵树 | 条目数从几百降到个位数 | 需自律 |
| 把 cargo `target` 与 gradle 缓存放在**空间宽裕的盘** | 减少 C: 压力 | 已做（都在 D:）|
| 关掉回收站（「不将文件移到回收站」）| 回收站恒为空 | **没有后悔药**，不推荐 |

## 5. 一次性释放那 11 GB（需要你操作）

我在 WorkBuddy 里删不掉（§3 已证明）。请**在你自己开的 PowerShell 窗口**里执行：

```powershell
cd C:\Users\tzh\Documents\code\HiFiShifter-mobile

# ① 先看会删什么（不动任何文件）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\clean-disk.ps1 -TempOlderThanDays 1 -MinFileMB 0

# ② 确认后真删 + 顺带清空回收站
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\clean-disk.ps1 `
    -TempOlderThanDays 1 -MinFileMB 0 -Apply -EmptyRecycleBin
```

**自检**：跑完再执行一次 `clean-disk.ps1`（不带 `-Apply`），第一行的「C: 可用」应该从 688 MB
涨到 10 GB 量级。**如果数字没动**，说明删除仍然被送进了回收站（即拦截是机器级的），
那就再加一步 `-EmptyRecycleBin` 即可 —— 无论哪种情况，这两步都能拿到空间。

脚本的白名单**刻意不含** 桌面 / 下载 / 文档 / 家目录根，且执行前会二次校验前缀；
`%TEMP%` 用 `$env:LOCALAPPDATA` 取路径（**不受本次 TEMP 改动影响**，仍精确指向 C: 那个旧目录）。

